# 旧系统到规则中心映射校验

> 基于旧系统源码逐行核对，验证 `docs/五院当前折价逻辑代码位置.md` 中的映射关系是否正确，并补充遗漏项。  
> 整理日期：2026-05-11

---

## 一、规则数据映射

### 1.1 FIN_DISCOUNT_FEE → 新规则表

| 旧字段 | 新系统对应 | 映射方式 | 备注 |
|--------|-----------|---------|------|
| `item_code` | `PR_RULE_CONDITION.CONDITION_VALUE` | `ITEM_MATCH` 条件 | 一对一映射 |
| `discount_rate` | `PR_RULE_ACTION.PARAMS_JSON` → `{"Rate": 0.5}` | `FORMULA_CALC` / `INCREMENT_PERCENT` | discount_rate 直接等于 Rate 参数 |
| `topprice` | `PR_RULE_ACTION.PARAMS_JSON` → `{"MaxAmount": x}` | `APPLY_MAX_AMOUNT` 独立动作 | 需单独添加一条 action 行 |
| `discount_type` | 不存储，以 action 是否存在为准 | — | "2"=有规则，建规则即代表有效 |
| `valid_state` | `PR_RULE_HEADER.STATUS` | "ACTIVE"/"INACTIVE" | 需转换 |

**迁移注意**：原来一行 FIN_DISCOUNT_FEE 迁移为：
- 1 条 `PR_RULE_HEADER`
- 1 条 `PR_RULE_CONDITION`（ITEM_MATCH）
- 1 条 `PR_RULE_ACTION`（FORMULA_CALC, INCREMENT_PERCENT）
- 若 topprice > 0：额外 1 条 `PR_RULE_ACTION`（APPLY_MAX_AMOUNT）

### 1.2 COM_DICTIONARY (Restrictingfee) → 新规则表

| 旧字段 | 新系统对应 | 映射方式 | 备注 |
|--------|-----------|---------|------|
| `code` | `PR_RULE_CONDITION.CONDITION_VALUE` | `ITEM_MATCH` 条件 | — |
| `input_code` | `PR_RULE_ACTION.PARAMS_JSON` → `{"LimitQty": x, "WindowMinutes": 120}` | `APPLY_TIME_WINDOW_LIMIT` | input_code 即 2 小时窗口内上限数量 |
| 无 | `PR_RULE_ACTION.PARAMS_JSON` → `{"MaxDailyQty": x}` | `APPLY_DAY_LIMIT_QTY` | 是否还需日限额取决于业务口径确认 |

### 1.3 COM_DICTIONARY (RestrictingfeeZT) → 新规则表

| 旧字段 | 新系统对应 | 映射方式 | 备注 |
|--------|-----------|---------|------|
| `code` | `PR_ITEM_GROUP_DETAIL.ITEM_CODE` | 分组明细 | — |
| `mark`（组号） | `PR_ITEM_GROUP.GROUP_CODE` | 项目分组 | — |
| 无 | `PR_RULE_ACTION` → `SAME_GROUP_MUTEX` | 同组互斥动作 | 需在规则中配置 |

---

### 1.4 常数类型 RestrictingfeeCP / RestrictingfeeTX1

| 旧类型 | 含义 | 新系统处理 |
|--------|------|-----------|
| `RestrictingfeeCP` | 床旁加收 2 小时共享额度 | `APPLY_TIME_WINDOW_LIMIT` + `SAME_GROUP_MUTEX`。旧 SQL 会汇总所有 CP 项目的 2 小时历史收费量，不能只做同项目限制 |
| `RestrictingfeeTX1` | 胎心监护组套限额 | 同 RestrictingfeeZT → `SAME_GROUP_MUTEX`，计划并入分组折价 |
| `Astrictpackagefee` | 组套内历史占用豁免项 | 旧逻辑命中时不查历史占用，但本次收费内仍会扣减；迁移时不要把它误建成独立折价规则 |

## 二、执行逻辑映射

| 旧方法 | 原逻辑 | 新执行器 | 是否正确 |
|--------|--------|---------|---------|
| `ConvertRestrictingfee` | CARD_NO+itemCode 查历史收费次数，超限归零 | `TimeWindowLimitExecutor` | ✅ 逻辑一致，维度改用 `PatientId:ItemCode` |
| `ConvertRestrictingfeeZY` | 同上，住院对象 | `TimeWindowLimitExecutor` + ChargeScene 条件 | ✅ 统一引擎处理，场景由条件区分 |
| `ConvertRestrictingfeeCharge` | 组套展开后逐明细折价再汇总 | 新系统中组套由 HIS 端拆开后逐项计价 | ⚠️ 见下方说明 |
| `ConvertDiscountfee` | 公式 = 单价×(qty×rate+(1-rate))，顶价截断 | `IncrementPercentExecutor` + `AmountCeilingExecutor` | ✅ 公式等价 |
| `ConvertDiscountfeeZY` | 同上，住院对象 | 同上 | ✅ |
| `getRestrictingfee` | SQL 查 2 小时内历史收费次数 | `LimitOccupyRepository.GetOccupiedQtyAsync` | ⚠️ 数据源不同，见第三节 |
| `getRestrictingfeeZT` | 按组号查历史收费次数 | `SameGroupMutexExecutor` + `PR_ITEM_GROUP` | ✅ 逻辑等价 |

### ConvertRestrictingfeeCharge 说明

旧系统中 `ConvertRestrictingfeeCharge` 专门处理"组套主项展开后按明细折价再还原给主项"。
新系统中，HIS 端在调用 confirm 接口时应**按展开后的明细项目逐条传入**，而不是传组套主项。因此 `ConvertRestrictingfeeCharge` 的展开行为由 HIS 客户端负责，计价引擎收到的是已展开的明细列表。需要 HIS 联调时确认。

## 三、数据源差异（最重要的架构差异）

| 维度 | 旧系统 | 新系统 |
|------|--------|--------|
| 历史收费来源 | 门诊/住院实际收费明细表（HIS 业务表） | `PR_LIMIT_OCCUPY` 表（规则中心自建） |
| 已收费次数获取 | 直接 SELECT 门诊/住院收费表 | SELECT PR_LIMIT_OCCUPY WHERE status IN ('PENDING','CONFIRMED') |
| 上线前历史数据 | 天然可见 | **完全不可见** → 上线当天已有收费不计入 |
| 跨渠道累计 | 所有渠道写同一张收费明细表，自然累计 | 所有渠道调用 confirm 接口，写入 PR_LIMIT_OCCUPY |

**结论**：上线方案必须考虑从旧收费明细表迁移当日已有限额数据，否则上线当天会出现同日重复超量收费。

## 四、现有文档映射表校验结果

来自 `docs/五院当前折价逻辑代码位置.md` 第五节：

| 文档映射 | 校验结果 |
|---------|---------|
| SetRestrictingfee → RuleMatchService + ItemMatchEvaluator | ✅ SetRestrictingfee 是"判断是否有规则"，等价于规则匹配命中 |
| SetDiscountfee → RuleMatchService + ItemMatchEvaluator | ✅ 同上 |
| ConvertRestrictingfee → TimeWindowLimitExecutor + DailyQtyLimitExecutor | ✅ 核心逻辑等价 |
| ConvertRestrictingfeeCharge → AddChildItemExecutor + SameGroupMutexExecutor | ⚠️ 部分正确：组套拆分应由 HIS 端完成，互斥逻辑由 SameGroupMutexExecutor 处理 |
| ConvertDiscountfee → IncrementPercentExecutor + AmountCeilingExecutor | ✅ 正确。旧系统**无最低限价**，不要为 FIN_DISCOUNT_FEE 生成 AmountFloorExecutor / APPLY_MIN_AMOUNT |
| getRestrictingfee → TimeWindowLimitExecutor + LimitOccupyRepository | ✅ 逻辑正确，数据源差异见第三节 |
| Restrictingfee 常数 → PR_RULE_CONDITION（ITEM_MATCH 条件） | ✅ |
| RestrictingfeeZT 常数 → PR_ITEM_GROUP + PR_ITEM_GROUP_DETAIL | ✅ |
| FIN_DISCOUNT_FEE → PR_RULE_ACTION（FORMULA_CALC ParamsJson） | ✅ 但同时还需 APPLY_MAX_AMOUNT |
| 三端各自入口 → 统一 /api/pricing/calculate/* | ⚠️ 自助机在旧系统不执行折价规则，迁移后是否应该执行需要业务确认 |
