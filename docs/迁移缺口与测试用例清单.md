## 一、迁移缺口清单

### P0 — 上线前必须解决

#### G-01：上线当天历史数据断层

**问题**：旧系统 `getRestrictingfee` 查的是 HIS 业务收费明细表（含当天已有收费）；新系统 `TimeWindowLimitExecutor` 查的是 `PR_LIMIT_OCCUPY`（上线前为空）。

**后果**：上线当天若患者上午在旧系统已收费 N 次，下午切新系统时新系统认为 0 次，会重复放行超限收费。

**解决方案（二选一）**：
- 方案A：上线前夜批量将当天旧收费明细写入 `PR_LIMIT_OCCUPY`（状态=CONFIRMED）
- 方案B：新系统在 `LimitOccupyRepository.GetOccupiedQtyAsync` 内增加兜底查询（SELECT 旧收费明细表作为补充来源），过渡期后移除

#### G-02：自助机是否执行折价的业务决策

**问题**：旧系统自助机 `GetFeeItemListnew` 全部折价代码被注释，自助机当前**不执行折价**。新系统统一入口默认会执行折价规则。

**后果**：迁移后自助机若触发折价规则，会改变价格，与旧行为不一致，可能影响患者收费。

**需确认**：彬哥/收费处确认自助机切入新系统后是否应该执行折价规则。

**若不执行**：需在相关规则的条件中增加 `SourceSystem != "ZZSB"` 过滤，或专门建自助机豁免条件。

#### G-03：微信端折价状态确认

**问题**：`OutpatientFeeSpecialRule.CTMRFeeRule` 源码为空壳；`RegisterInfoManager.GetFeeItemList` 未调用折价方法。当前微信端**不执行任何折价**。

**需确认**：微信端迁移后是否应执行折价规则（现状是不折价，文档中原来认为有折价是错误的）。

#### G-04：getRestrictingfee 实际 SQL 已补充，仍需上线前抽样核对

**当前状态**：用户已补充 `legacy-code/HIS-Use/辅助说明.txt`，其中包含 `Fee.PactUnitItemRate.RestrictingfeePay2` 和 `Fee.PactUnitItemRate.RestrictingfeePayZT` 的 SQL 片段。已确认旧 HIS 的数量限制和 ZT/TX1 互斥口径按最近 2 小时窗口查询，不是自然日整天累计。

**仍需动作**：上线前用真实 HIS 收费明细抽样核对退费、重收、套餐编码、床旁项目等边界条件，确认 SQL 片段和生产库配置完全一致。

**已落实到代码**：`SameGroupMutexExecutor` 已从按自然日累计修正为 `WindowMinutes` 滑动窗口，默认 120 分钟。

**已落实到导入脚本**：`sql/04-import-rules.sql` 已给 `RestrictingfeeCP` 补充同组互斥规则，用于复刻旧 SQL “所有床旁项目共享 2 小时额度”的口径；`RestrictingfeeZT`、`RestrictingfeeTX1` 和 `RestrictingfeeCP` 均补充了 7021 科室排除条件。

### P1 — 第一阶段上线前解决

#### G-05：挂号部(7021)排除条件已补入导入脚本，仍需上线前抽样核对

**问题**：旧系统代码 `if (returnRows > 0 && 部门 != "7021")` 明确排除挂号部。迁移后必须保证数量折价、CP、ZT、TX1 等规则都保留该排除条件。

**当前状态**：`sql/04-import-rules.sql` 已为 RF、CP、ZT、TX1 规则补入 `CHARGE_DEPT_EXCLUDE = 7021` 条件；`sql/99-verify.sql` 已补对应校验。

**仍需动作**：上线前执行导入验证脚本，并抽样确认实际发布规则均带 7021 排除条件。

#### G-06：FIN_DISCOUNT_FEE 无最低限价，但旧文档提到最低限价

**问题**：`FIN_DISCOUNT_FEE` 表结构中只有 `topprice`（最高限价），无最低限价字段。旧代码 `SetDiscountfee` 只返回 DISCOUNT_RATE 和 TOPPRICE。

**后果**：新系统中的 `AmountFloorExecutor` 在 74 条历史规则迁移时**无对应数据**，不应为这些规则创建 `APPLY_MIN_AMOUNT` 动作。

#### G-07：AREA_STEP_INCREMENT 执行器已实现，业务参数仍需核定（B-5类，17条规则）

**当前状态**：`src/Pricing.RuleCenter.Core/Engine/Executors/AreaStepIncrementExecutor.cs` 已实现 `AREA_STEP_INCREMENT`，并已注册到 API DI。测试 `AreaStepIncrementExecutorTests` 已覆盖基础面积、超出面积、多个面积片段等口径。

**影响规则**：带蒂皮瓣转移费、游离皮瓣移植费、游离复合组织瓣移植费、带蒂复合组织瓣转移费（17条）。

**公式**：`amount = unitPrice × (1 + ceil((area - baseArea) / baseArea) × stepRate)`，baseArea=15cm²，stepRate=15%。

**仍需动作**：同手术封顶金额、具体项目封顶金额、面积边界口径需要业务确认后补入规则数据。

#### G-08：CONVERT_QTY_BY_PART + 单肿物封顶执行器已实现，规则参数仍需补齐（B-4类，24条规则）

**当前状态**：`src/Pricing.RuleCenter.Core/Engine/Executors/ConvertQtyByPartExecutor.cs` 已实现按部位面积换算数量、单病灶封顶和多病灶金额汇总，执行器编码为 `CONVERT_QTY_BY_PART`。测试 `ConvertQtyByPartExecutorTests` 覆盖部位换算、默认面积、单病灶封顶和多病灶累计。

**影响规则**：巨痣、血管瘤、脉管畸形、神经纤维瘤及其各子项，共 24 条。

**仍需动作**：需要把每个部位的 `BaseArea`、每个项目的 `MaxAmountPerLesion` 从规则清单或业务确认结果写入导入脚本；否则执行器有能力，但规则无法完整落地。

#### G-09：CHILD_ITEM_PERCENT 执行器已实现，父子项目排序和规则参数仍需落地

**当前状态**：`src/Pricing.RuleCenter.Core/Engine/Executors/ChildItemPercentExecutor.cs` 已实现儿童加收公式，按父项目最终金额乘以 `ChildRate` 或 `ChildPercent` 计算，执行器编码为 `CHILD_ITEM_PERCENT`。测试 `ChildItemPercentExecutorTests` 已覆盖父项目金额百分比、缺少父项时跳过等口径。

**仍需动作**：调用方批量计价时必须保证父项目先于儿童加收子项；导入规则时必须配置 `ParentItemCode` 和加收比例。

#### G-10：同手术封顶金额待补充（B-5类）

**问题**：带蒂皮瓣等项目的"单条封顶金额"和"同手术封顶金额"在 Excel 规则清单中只写"有最高限价"，具体金额未填写。
