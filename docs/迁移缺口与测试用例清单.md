## 一、迁移缺口清单

### P0 — 上线前必须解决

#### G-01：上线当天历史数据断层

**问题**：旧系统 `getRestrictingfee` 查的是 HIS 业务收费明细表（含当天已有收费）；新系统 `TimeWindowLimitExecutor` 查的是 `PR_LIMIT_OCCUPY`（上线前为空）。

**后果**：上线当天若患者上午在旧系统已收费 N 次，下午切新系统时新系统认为 0 次，会重复放行超限收费。

**解决方案（二选一）**：
- 方案A：上线前夜批量将当天旧收费明细写入 `PR_LIMIT_OCCUPY`（状态=CONFIRMED）
- 方案B：新系统在 `LimitOccupyRepository.GetOccupiedQtyAsync` 内增加兜底查询（SELECT 旧收费明细表作为补充来源），过渡期后移除

#### G-02：自助机是否执行折价的业务决策

**问题**：旧系统自助机 `GetFeeItemListnew` 全部折价代码被注释，自助机当前**不执行折价**。新系统统一入口默认会执行折价规则。

**后果**：迁移后自助机若触发折价规则，会改变价格，与旧行为不一致，可能影响患者收费。

**需确认**：彬哥/收费处确认自助机切入新系统后是否应该执行折价规则。

**若不执行**：需在相关规则的条件中增加 `SourceSystem != "ZZSB"` 过滤，或专门建自助机豁免条件。

#### G-03：微信端折价状态确认

**问题**：`OutpatientFeeSpecialRule.CTMRFeeRule` 源码为空壳；`RegisterInfoManager.GetFeeItemList` 未调用折价方法。当前微信端**不执行任何折价**。

**需确认**：微信端迁移后是否应执行折价规则（现状是不折价，文档中原来认为有折价是错误的）。

#### G-04：getRestrictingfee 实际 SQL 未获取

**问题**：`getRestrictingfee` 和 `getRestrictingfeeZT` 通过 SQL 配置索引 `"Fee.PactUnitItemRate.RestrictingfeePay2"` 和 `"Fee.PactUnitItemRate.RestrictingfeePayZT"` 加载 SQL，这两条 SQL 尚未从 HIS 配置文件中提取。

**后果**：无法确认旧系统 2 小时窗口的精确口径（是向前 2 小时？还是自然日？是否包含退费？），新系统 `TimeWindowLimitExecutor` 的默认 120 分钟是否与旧系统完全一致存疑。

**解决方案**：从内网 HIS 配置文件（通常是 `.xml` 或 `.config`）中提取 `RestrictingfeePay2` 和 `RestrictingfeePayZT` 对应的完整 SQL。

### P1 — 第一阶段上线前解决

#### G-05：挂号部(7021)排除条件未迁移

**问题**：旧系统代码 `if (returnRows > 0 && 部门 != "7021")` 明确排除挂号部。新系统规则条件中无此排除。

**解决方案**：为所有数量折价规则增加 ChargeScene 条件排除挂号部，或在规则发布时作为约束说明。

#### G-06：FIN_DISCOUNT_FEE 无最低限价，但旧文档提到最低限价

**问题**：`FIN_DISCOUNT_FEE` 表结构中只有 `topprice`（最高限价），无最低限价字段。旧代码 `SetDiscountfee` 只返回 DISCOUNT_RATE 和 TOPPRICE。

**后果**：新系统中的 `AmountFloorExecutor` 在 74 条历史规则迁移时**无对应数据**，不应为这些规则创建 `APPLY_MIN_AMOUNT` 动作。

#### G-07：AREA_STEP_INCREMENT 执行器缺失（B-5类，17条规则）

**问题**：文档 `12-历史规则分类与公式定义.md` 中 B-5 类 17 条规则需要执行器 `AREA_STEP_INCREMENT`（面积分段递增公式），当前执行器目录中**没有该执行器**。

**影响规则**：带蒂皮瓣转移费、游离皮瓣移植费、游离复合组织瓣移植费、带蒂复合组织瓣转移费（17条）。

**公式**：`amount = unitPrice × (1 + ceil((area - baseArea) / baseArea) × stepRate)`，baseArea=15cm²，stepRate=15%。

#### G-08：CONVERT_QTY_BY_PART + 单肿物封顶执行器缺失（B-4类，24条规则）

**问题**：B-4 类需要执行器：
1. `CONVERT_QTY_BY_PART`（按部位换算面积→数量，不同部位不同换算基数）
2. 单肿物封顶（每个肿物独立封顶，多肿物相加）
3. `CHILD_ITEM_PERCENT`（儿童加收项目：金额=主项目最终金额×30%）

当前均**未实现**。

**影响规则**：巨痣、血管瘤、脉管畸形、神经纤维瘤及其各子项，共 24 条。

#### G-09：CHILD_ITEM_PERCENT 执行器缺失

**问题**：儿童加收项目（如"浅表肿物去除费-儿童(加收)"）的计价公式是 `childAmount = mainItemFinalAmount × 30%`，基准是**主项目经过公式+封顶后的最终金额**，不是简单的 `unitPrice × qty`。

当前 `AddChildItemExecutor` 处理的是自动附加子项（按主项目数量加收），**不能**直接处理"儿童加收"这种基于主项目金额百分比的加收逻辑。

#### G-10：同手术封顶金额待补充（B-5类）

**问题**：带蒂皮瓣等项目的"单条封顶金额"和"同手术封顶金额"在 Excel 规则清单中只写"有最高限价"，具体金额未填写。

**需动作**：从运营/业务处获取具体封顶金额，补充到 `12-历史规则分类与公式定义.md`。

## 二、测试用例清单

### T-01：基础 2 小时窗口限额（A 类，20 条规则）

| 用例 | 输入 | 期望输出 | 验证点 |
|------|------|---------|--------|
| T-01-1 窗口内未超限 | 患者 P001，CT 平扫，2 小时内已收 1 次，本次 1 次，limit=3 | 全量收费，FinalAmount = 单价 | 剩余额度 = 2，不截断 |
| T-01-2 窗口内正好达上限 | 同患者，已收 2 次，本次 1 次，limit=3 | 全量收费 | 剩余额度 = 1，刚好满足 |
| T-01-3 窗口内超限（数量截断） | 同患者，已收 2 次，本次 2 次，limit=3 | FinalQty=1，FinalAmount 按比例缩减 | 超出部分归零，金额等比缩放 |
| T-01-4 窗口内已达上限 | 同患者，已收 3 次，本次 1 次，limit=3 | FinalQty=0，FinalAmount=0 | 完全超限 |
| T-01-5 试算不占额 | 同上，调 simulate 两次 | 两次均返回 0 | simulate 不写 PR_LIMIT_OCCUPY |
| T-01-6 跨整点边界 | 10:01 收费，2 小时窗口覆盖 08、09、10 三个小时桶 | 锁定 3 个桶 | 验证 BuildLockKeys 枚举正确 |
| T-01-7 补录历史收费 | BusinessChargeTime=昨天，今天调接口 | 进入昨天日期的桶，不影响今天额度 | 业务时间优先 |
| T-01-8 confirm 后 commit | confirm 成功，HIS 落账，调 commit | PR_LIMIT_OCCUPY 状态从 PENDING → CONFIRMED | 状态机正确 |
| T-01-9 confirm 后 cancel | confirm 成功，调 cancel | PR_LIMIT_OCCUPY 状态 → CANCELLED，额度释放 | 取消后下次可重新收费 |
| T-01-10 当日退费释放额度 | 当日收费后退费，reverse | PR_LIMIT_OCCUPY 写负向占额，净额度增加 | 退费当天释放 |
