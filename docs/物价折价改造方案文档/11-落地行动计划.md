## 阶段一：需求澄清（预计 1-2 天）

你需要找业务方（物价管理员或项目负责人）确认以下问题，把答案填在每条后面。

### 1.1 业务口径确认

- [x] **"单次"的定义是什么？**
  - 单条收费明细 / 单次收费动作 / 单台手术 / 单次医嘱执行？
  - 答案：【单次】指单次收费动作，包括门诊收费保存、手术/医技划价、终端确认、护士过医嘱/分解医嘱；【单条】指单条收费明细。

- [x] **"折价项目"和"特殊项目"是否同一个概念？**
  - 是同一个标识，还是折价是特殊的子集？
  - 答案：是同一个标识。折价项目就是中山一方案中的特殊项目，仅名称不同。

- [x] **一个项目是否允许维护多条规则？**
  - 例如同一项目头面部一条规则、躯干部一条规则
  - 答案：允许同一项目按不同部位维护不同换算规则；不允许同一项目维护不同折价公式、不同折价额度规则。

- [x] **退费是否释放额度？**
  - 全额退费释放全部？部分退费按数量释放？隔日退费释放哪天的？
  - 答案：退费按退费数量释放额度；当日退费释放数量，隔日退费重收后按重收当天重新做额度校验。2 小时规则按收费时间（包含重收时间）向前查 2 小时，判断是否超过限制。
  - 补充：现有开发逻辑主要关注重收时校验，之前没有明确“释放额度”概念；刘晗退费代码中有字段记录重收前数量。返还额度的具体实现方式仍需彬哥和收费处进一步确认。

- [x] **全院累计的统计范围？**
  - 门诊算不算？住院算不算？急诊算不算？自助机算不算？已退费的算不算？
  - 答案：全院按收费途径统计，包括门诊收费、手术/医技划价、终端确认、护士过医嘱/分解医嘱；已退费不计入累计。

- [x] **金额取整规则？**
  - 中间计算保留几位？最终金额保留几位？四舍五入还是向上取整？
  - 答案：中间计算保留全部精度；最终金额保留 2 位小数，四舍五入。

### 1.1.1 业务口径对应改造逻辑

以下 6 项不是只作为备注保存，后续编码和验收必须按本节落地。

| 口径 | 改造逻辑 | 当前状态 |
| --- | --- | --- |
| 单次 / 单条 | 一次 `PricingCalculateRequest` 表示一次收费动作；`businessRequestNo` 表示本次收费动作的稳定业务号；`items[]` 表示本次收费动作下的多条收费明细。单次限额不能再按单条明细号判断，应按 `sourceSystem + businessRequestNo + itemCode` 或同等收费动作维度累计；单条追溯和落账仍使用 `chargeDetailNo`。 | 已按 `items[]` 拆分入参并补齐 `APPLY_ONCE_LIMIT_QTY`，同请求内多明细共享单次额度 |
| 折价项目 / 特殊项目 | 两者使用同一个项目标识和同一套规则表，不新增第二套“折价项目”标识。`special-flag` 查询命中已发布启用规则即认为是特殊/折价项目；HIS 页面可按本地名称展示，但接口和表结构只维护一个口径。 | 接口命名已使用 special-flag；文档需保持同义说明 |
| 一个项目多条规则 | 数据模型允许同一项目多条规则，但发布校验必须限制冲突：同一项目、同一场景、同一生效区间内，允许不同部位有不同 `CONVERT_QTY` 换算规则；不允许多个 `FORMULA_CALC`、金额上下限、单日/单次/2 小时额度规则同时生效。部位条件为空视为覆盖全部部位，不能与具体部位规则冲突。 | 已补发布前冲突校验；部位分流仅对换算规则放行 |
| 退费释放额度 | `reverse` 不能只把原请求整体标记为 `REVERSED`。退费应按 `chargeDetailNo/itemCode/partSeq` 定位原折价明细，校验“本次退费数量 + 历史已退数量 <= 原有效收费数量”。当日退费生成负向占额释放原数量；隔日退费不回写历史窗口给历史日复用，重收按重收收费时间重新调用计价并参与重收当天额度校验。2 小时窗口始终按收费/重收时间向前查 2 小时。返还额度的具体落库方式仍需收费处确认。 | 已支持部分退费、历史已退校验和当日负向占额；隔日仅记冲正不回写历史窗口 |
| 全院累计范围 | 全院累计按收费途径汇总：门诊收费、手术/医技划价、终端确认、护士过医嘱/分解医嘱。限额累计查询只统计有效占用状态：`PENDING`、`CONFIRMED`；排除 `CANCELLED`、`EXPIRED`、`REVERSED`，并扣减已确认退费负向占额。后续如果存在非计价中心来源收费，必须先接入统一占额表或统一查询视图，不能只查单一 HIS 表。 | 已补收费场景编码集合和字典；累计查询按占额表有效状态净额统计并扣减负向退费 |
| 金额取整 | 规则执行中间值不主动取整；最终对外金额和落账金额统一 `roundScale = 2`，四舍五入。C# 应使用 `decimal` 和 `MidpointRounding.AwayFromZero`，禁止用 `double/float`；限额按比例截断时不要提前截成 4 位后继续算，最终出响应/落库前统一取 2 位。 | 已补统一取整组件，最终响应/落账 2 位四舍五入，限额比例截断不再中途 4 位取整 |
