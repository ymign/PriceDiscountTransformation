# 资金风险补齐方案

## 1. 文档目的

本文用于补齐 01-09 方案中仍可能导致错收费、重复占额、漏折价的风险点。

本文结论优先级高于早期文档中的宽泛表述。后续编码、联调、测试、上线必须按本文约束执行。

## 2. 总体结论

当前统一计价规则中心方向正确，但以下内容必须在编码前补齐：

1. 幂等键和请求指纹。
2. 2 小时滑动窗口锁粒度。
3. confirm、commit、cancel、reverse、expire 状态机。
4. 公式项目与数量限制、同手术封顶的关系。
5. 批量试算的组内互斥和同批累计。
6. 多肿物、多部位、多面积输入模型。
7. 单价来源和校验。
8. 规则发布冲突校验。
9. 主子项目原子落账。
10. 灰度回滚边界。

这些不是优化项，而是资金安全底线。

## 3. 必须补齐的 P0 项

## 3.1 confirm 幂等必须基于稳定业务号和请求指纹

### 风险

如果 HIS 在 confirm 超时后重新生成新的 `requestNo`，计价中心会认为是新请求，可能重复占额、重复写折价明细。

如果幂等参数只比较 `itemCode`、`inputQty`、`patientId`、`unitPrice`，会漏掉部位、收费时间、手术号、孕次号、扩展参数等关键字段。同一个请求号下参数实际变了，计价中心仍可能返回旧结果。

### 补齐规则

confirm、commit、cancel、reverse 必须使用调用方稳定业务号。

建议幂等键：

```
sourceSystem + businessRequestNo + callType
```

其中 `businessRequestNo` 不应由每次 HTTP 调用随机生成，必须能稳定映射到 HIS 的一次收费确认动作。推荐来源：

| 场景 | businessRequestNo 建议 |
| --- | --- |
| HIS 已生成收费明细号 | `chargeNo + chargeDetailNo` |
| HIS 尚未生成收费明细号 | HIS 本地预生成的收费确认流水 |
| 自助机支付前确认 | 订单号 + 项目序号 |
| 微信支付前确认 | 订单号 + 项目序号 |
| reverse | 原收费明细号 + 退费流水号 |

### 请求指纹

计价中心必须保存 `REQUEST_FINGERPRINT`。重复请求时比较指纹，而不是只比较少数字段。

指纹计算前，必须对以下内容做规范化：

1. 字段名统一。
2. 字符串 trim。
3. 空字符串按 NULL 处理。
4. 金额、数量统一 decimal 格式。
5. `extraParams` 按键名排序。
6. `pricingParts` 按调用方传入的 `partSeq` 排序。

指纹至少包含：

| 字段组 | 字段 |
| --- | --- |
| 请求身份 | `sourceSystem`、`businessRequestNo`、`callType` |
| 患者就诊 | `patientId`、`visitId`、`encounterNo` |
| 收费场景 | `chargeScene`、`chargeNo`、`chargeDetailNo` |
| 项目信息 | `itemCode`、`itemName`、`inputQty`、`inputUnit` |
| 业务时间 | `chargeTime` |
| 条件字段 | `bodyPartCode`、`operationNo`、`pregnancyNo`、`mainChargeDetailNo` |
| 扩展输入 | `extraParams` 全量规范化 JSON |
| 多部位明细 | `pricingParts` 全量规范化 JSON |
| 价格校验 | `unitPrice` 或计价中心读取到的权威单价版本 |

### 接口行为

重复请求处理：

1. 幂等键不存在：正常处理并保存请求、响应、指纹。
2. 幂等键存在且指纹一致：返回首次响应，不重复占额。
3. 幂等键存在但指纹不一致：返回 `IDEMPOTENT_CONFLICT`，不得覆盖旧记录。

HIS 调用规范：

1. 业务动作重试必须复用同一个 `businessRequestNo`。
2. 用户修改参数后必须生成新的 `businessRequestNo`。
3. HTTP 超时不代表失败，必须先用同一业务号重试或查询原结果。

## 3.2 2 小时滑动窗口必须按业务发生时间和覆盖小时加锁

### 风险

早期方案按当前小时和前一小时加锁，在整点边界可能漏锁。

示例：

- 当前收费时间：10:01。
- 2 小时窗口：08:01 到 10:01。
- 涉及 08、09、10 三个小时桶。
- 只锁 09、10 会漏掉 08:30 的确认请求并发影响。

如果使用 `OCCUPIED_AT` 作为累计时间，补录、补缴费、延迟提交也可能把原业务时间算错。

### 补齐规则

限额累计必须区分：

| 字段 | 含义 |
| --- | --- |
| `BUSINESS_CHARGE_TIME` | HIS 业务收费发生时间，用于规则生效和窗口累计 |
| `OCCUPIED_AT` | 计价中心占额记录创建时间，用于技术审计 |
| `CONFIRMED_AT` | 业务系统落账通知时间 |

`PR_LIMIT_OCCUPY` 必须增加或等价保存 `BUSINESS_CHARGE_TIME`。

### 滑动窗口锁定算法

对任意 `TIME_WINDOW_MINUTES`：

1. `windowStart = chargeTime - TIME_WINDOW_MINUTES`
2. `windowEnd = chargeTime`
3. 枚举 `[windowStart, windowEnd]` 覆盖到的所有小时桶。
4. 为每个小时桶生成 `TW:{patientId}:{itemOrGroup}:{yyyyMMddHH}`。
5. 按字典序创建并 `SELECT ... FOR UPDATE` 锁定全部锁行。
6. 锁定后按 `BUSINESS_CHARGE_TIME` 查询窗口内 `PENDING`、`CONFIRMED` 的净占用。

2 小时窗口最多覆盖 3 个小时桶，不能只锁当前小时和前一小时。

### 查询口径

```sql
SELECT NVL(SUM(OCCUPY_QTY), 0)
FROM PR_LIMIT_OCCUPY
WHERE LIMIT_TYPE = 'TIME_WINDOW'
  AND LIMIT_DIMENSION_CODE = :dimensionCode
  AND STATUS IN ('PENDING', 'CONFIRMED')
  AND BUSINESS_CHARGE_TIME >= :windowStart
  AND BUSINESS_CHARGE_TIME <= :windowEnd
```

不要只依赖 `LIMIT_KEY LIKE` 查询。建议额外存 `LIMIT_DIMENSION_CODE`，例如 `patientId + itemCode` 或 `patientId + groupCode`，用于稳定查询。

## 3.3 状态机必须覆盖请求、占额、折价明细三类记录

### 风险

只更新 `PR_LIMIT_OCCUPY.STATUS` 不够。请求日志、折价明细、子项目结果如果状态不同步，会进入报表或对账口径，形成假收费或漏冲正。

### 补齐状态

`PR_CHARGE_REQUEST_LOG` 建议增加业务状态：

| 状态 | 含义 |
| --- | --- |
| `SIMULATED` | 试算完成 |
| `CONFIRM_PENDING` | confirm 成功，待业务系统落账 |
| `CONFIRMED` | commit 成功 |
| `CANCELLED` | cancel 成功 |
| `EXPIRED` | confirm 超时释放 |
| `REVERSED` | 已被 reverse 冲正 |
| `FAILED` | 计价失败 |

`PR_CHARGE_DISCOUNT_DETAIL` 必须增加或等价保存：

| 字段 | 说明 |
| --- | --- |
| `STATUS` | PENDING、CONFIRMED、CANCELLED、EXPIRED、REVERSED |
| `COMMITTED_AT` | 落账确认时间 |
| `CANCELLED_AT` | 取消时间 |
| `EXPIRED_AT` | 过期时间 |
| `REVERSED_AT` | 冲正时间 |

`PR_LIMIT_OCCUPY`、`PR_CHARGE_REQUEST_LOG`、`PR_CHARGE_DISCOUNT_DETAIL` 的状态更新必须在同一事务内完成。

### 状态流转

```text
simulate:
  none -> SIMULATED

confirm:
  none -> CONFIRM_PENDING
  同时写 PENDING 占额和 PENDING 折价明细

commit:
  CONFIRM_PENDING -> CONFIRMED
  同时将占额和折价明细置为 CONFIRMED

cancel:
  CONFIRM_PENDING -> CANCELLED
  同时将占额和折价明细置为 CANCELLED

expire:
  CONFIRM_PENDING -> EXPIRED
  同时将占额和折价明细置为 EXPIRED

reverse:
  CONFIRMED -> REVERSED 或部分 REVERSED
  插入负数占额和冲正明细，保留原记录
```

### commit 与 expire 竞态

清理任务不能用单条 SQL 直接把所有过期占额改为 `EXPIRED`。

必须逐笔处理：

1. 锁定请求记录。
2. 检查是否已经收到 commit。
3. 检查 HIS 是否已有落账明细。
4. 确认未落账时，才更新为 `EXPIRED`。
5. 写清理日志。

commit 必须检查：

1. 当前状态必须是 `CONFIRM_PENDING`。
2. 当前时间必须小于 `expireAt`。
3. HIS 传入金额、数量、收费明细号必须与 confirm 响应一致。
4. 过期后 commit 返回 `EXPIRED`，HIS 必须重新 confirm。

## 3.4 公式项目不能全局跳过数量类限制

### 风险

早期需求里写“使用公式计价的项目，不会存在数量上下限”。但历史规则中大量项目同时存在：

- 公式计价。
- 单条医嘱封顶。
- 同一手术封顶。
- 多肿物相加。
- 主子项目加收。
- 部位基础量不同。

如果实现成“有公式就跳过全部数量限制”，会直接多收费。

### 补齐规则

只能跳过明确配置为与公式互斥的动作，不能按公式存在与否自动跳过。

执行原则：

1. 公式动作负责计算基础金额或基础计价数量。
2. 金额上下限动作仍然执行。
3. 同组互斥、同手术封顶、同孕次封顶仍然执行。
4. 单日、时间窗、单次数量限制是否执行，由规则动作显式配置。
5. 如果某项目确实“公式项目无数量限制”，必须在规则配置中不配置数量限制动作，而不是代码硬跳过。

建议废弃“公式项目无数量限制”作为全局硬编码规则，改成：

> 公式项目默认不自动继承数量限制；是否应用数量、时间窗、同组、同手术限制，以命中的规则动作配置为准。

## 3.5 批量试算必须支持同批上下文

### 风险

批量试算如果“每个项目独立计算，互不影响”，无法覆盖：

- 同胎次多个产科彩超超过 1 个按 1 个收费。
- 同组加收项目超过 1 个按 1 个收费。
- 同一手术同组封顶。
- 同一批次中同项目多行累计超过上限。

### 补齐规则

保留单项结果独立返回，但计算必须共享 `BatchPricingContext`。

批量试算流程：

1. 先按批次读取全部项目。
2. 构造同批内临时累计：患者、项目、组、手术号、孕次号、收费时间。
3. 对同组互斥、同手术封顶、同胎次封顶，先在批内排序和分配额度。
4. 再叠加历史已确认和待确认占用。
5. 最后返回每个项目的单项结果。

约束：

1. `batch-simulate` 不占正式额度。
2. `batch-confirm` 如后续提供，必须整体事务确认。任一项目失败，整批失败或按业务明确允许部分成功。
3. 当前只有 `batch-simulate` 时，HIS 仍必须逐项或整批 confirm，不能拿 batch-simulate 结果直接落账。
4. 响应必须返回批内互斥说明，例如“本批第 2 个同胎次项目因第 1 个已占用额度，本项折价为 0”。

## 3.6 多肿物、多部位、多面积必须用明细数组表达

### 风险

单个 `inputQty`、`bodyPartCode`、`area` 无法表达：

- 一个收费项目下多个肿物。
- 每个肿物不同部位。
- 每个肿物不同面积。
- 每个肿物单独封顶后再汇总。

### 补齐请求模型

统一请求中增加 `pricingParts`：

```json
{
  "itemCode": "SKIN_TUMOR_001",
  "inputQty": 2,
  "pricingParts": [
    {
      "partSeq": 1,
      "bodyPartCode": "HEAD",
      "measureType": "AREA",
      "measureValue": 8,
      "measureUnit": "CM2",
      "lesionCount": 1
    },
    {
      "partSeq": 2,
      "bodyPartCode": "TRUNK",
      "measureType": "AREA",
      "measureValue": 144,
      "measureUnit": "CM2",
      "lesionCount": 1
    }
  ]
}
```

规则：

1. 没有多部位、多肿物时，`pricingParts` 可为空。
2. 只要规则需要单肿物封顶、分部位基础量、多面积计算，`pricingParts` 必填。
3. 引擎按 part 单独换算、公式、单条封顶，再汇总到主项目。
4. 追溯日志必须记录每个 part 的输入、换算、封顶、金额。

## 3.7 单价必须来自权威物价主数据或强校验

### 风险

如果计价中心直接信任渠道传入 `unitPrice`，任何渠道传错单价都会导致计价中心算出错误金额。

### 补齐规则

推荐模式：

1. 请求传 `itemCode`、`chargeTime`。
2. 计价中心从 HIS 权威物价主数据或同步表读取单价。
3. 响应返回 `priceVersion` 或 `priceEffectiveTime`。

兼容模式：

1. 渠道仍传 `unitPrice`。
2. 计价中心读取权威单价进行比较。
3. 不一致时返回 `PRICE_MISMATCH`，不得继续 confirm。
4. 只有影子模式或明确配置允许时，才可记录告警后继续试算。

所有金额计算必须以计价中心确认的权威单价为准。

## 3.8 规则发布必须做重叠和冲突校验

### 风险

同一项目、同一时间、同一场景、同一部位、同一动作组如果存在多条已发布规则，可能重复换算、重复封顶或顺序不稳定。

### 补齐规则

发布前必须校验：

| 校验 | 阻断条件 |
| --- | --- |
| 生效区间重叠 | 同规则同版本以外，时间区间交叉且未配置优先级和互斥组 |
| 动作组冲突 | 同一 `EXCLUSIVE_GROUP` 下有多条同优先级动作 |
| 换算冲突 | 同一项目、场景、部位命中多个 `CONVERT_QTY` |
| 公式冲突 | 同一项目、场景、部位命中多个 `FORMULA_CALC` |
| 封顶冲突 | 同一 LIMIT_TYPE 生成相同维度但上限值不同 |
| 子项目冲突 | 同一主项目条件下生成重复子项目 |
| 缺少测试用例 | 发布规则没有正向和边界测试 |

冲突必须阻断发布，除非维护人员明确配置：

1. 不同优先级。
2. 不同 `EXCLUSIVE_GROUP`。
3. 明确允许叠加的 `STACK_GROUP`。

发布成功后必须立刻失效规则缓存。

## 3.9 主子项目必须按一组结果原子落账

### 风险

儿童加收、功能部位加收等子项目依赖主项目结果。主项目落账成功但子项目失败，或者子项目落账成功但主项目失败，都会造成金额不一致。

### 补齐规则

计价响应必须把主项目和子项目放在同一个 `pricingResultGroup` 中：

```json
{
  "traceId": "TR001",
  "resultGroupNo": "GRP001",
  "mainItem": {
    "itemCode": "MAIN001",
    "finalAmount": 900
  },
  "childItems": [
    {
      "itemCode": "ADDON_CHILD",
      "baseItemCode": "MAIN001",
      "finalAmount": 270
    }
  ],
  "groupFinalAmount": 1170
}
```

HIS 处理规则：

1. main 和 child 必须同组写入 HIS。
2. 全组写入成功后再 commit。
3. 任一明细写入失败，必须 cancel 全组。
4. commit 请求必须带回 HIS 生成的所有 `chargeDetailNo`。
5. 计价中心按组更新状态。

## 3.10 回滚不能无条件切回普通计价

### 风险

文档中“回滚后所有渠道自动走旧逻辑”与“特殊项目不降级”存在冲突。

如果旧逻辑不存在或旧逻辑未覆盖新规则，直接走普通计价会多收费或少收费。

### 补齐规则

每个特殊项目必须维护 `rollbackMode`：

| rollbackMode | 含义 | 行为 |
| --- | --- | --- |
| `LEGACY_EQUIVALENT` | 旧逻辑与新规则等价 | 可切回旧逻辑 |
| `MANUAL_REVIEW` | 无等价旧逻辑，但可人工处理 | 暂停自动收费，转人工 |
| `STOP_CHARGE` | 无安全回退路径 | 暂停收费 |
| `NEW_SERVICE_ONLY` | 只能走新计价服务 | 服务异常时不可收费 |

灰度和全局回滚只能影响 `LEGACY_EQUIVALENT` 项目。其他特殊项目不能因为全局开关关闭就自动按普通单价收费。

## 4. P1 补齐项

## 4.1 部分退费必须校验累计已退

部分退费时不能只校验本次退费数量小于原确认数量，还要校验：

```
本次退费数量 + 历史已退数量 <= 原有效收费数量
本次退费金额 + 历史已退金额 <= 原有效收费金额
```

退费释放额度必须使用原记录的 `LIMIT_KEY`、`LIMIT_TYPE`、`BUSINESS_CHARGE_TIME`。

对多 part 项目，退费请求必须明确退哪个 `partSeq` 或按比例退。无法明确时，不允许自动释放额度，必须人工审核。

## 4.2 ON_ERROR 默认必须 STOP

资金相关动作默认错误策略：

| 动作 | 默认 ON_ERROR |
| --- | --- |
| `CONVERT_QTY` | STOP |
| `FORMULA_CALC` | STOP |
| `APPLY_MAX_AMOUNT` | STOP |
| `APPLY_MIN_AMOUNT` | STOP |
| `APPLY_DAY_LIMIT_QTY` | STOP |
| `APPLY_TIME_WINDOW_LIMIT` | STOP |
| `SAME_GROUP_MUTEX` | STOP |
| `ADD_CHILD_ITEM` | STOP |

只有纯提示、非金额影响动作可配置为 `WARN`。禁止资金动作配置为 `SKIP` 后继续收费。

## 4.3 对账必须覆盖本文新增口径

每日对账新增检查：

1. 同一幂等键多条成功 confirm。
2. 同一收费明细号多条 `CONFIRMED` 折价明细。
3. `CONFIRMED` 请求但折价明细仍为 `PENDING`。
4. `EXPIRED` 后 HIS 实际落账。
5. 2 小时窗口跨小时边界累计异常。
6. batch-simulate 结果被直接落账但无 confirm。
7. 特殊项目回滚后走普通计价。
8. 子项目缺失或主子项目金额不一致。
9. 退费累计释放超过原占用。
10. 规则发布后出现同项目同条件多条同优先级命中。

## 5. 必须补充的数据字段

建议在 04 表设计基础上补充：

### PR_CHARGE_REQUEST_LOG

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `BUSINESS_REQUEST_NO` | `VARCHAR2(80)` | 调用方稳定业务号 |
| `REQUEST_FINGERPRINT` | `VARCHAR2(128)` | 规范化请求指纹 |
| `BUSINESS_STATUS` | `VARCHAR2(30)` | SIMULATED、CONFIRM_PENDING、CONFIRMED 等 |
| `RESULT_GROUP_NO` | `VARCHAR2(80)` | 主子项目同组结果号 |
| `PRICE_VERSION` | `VARCHAR2(50)` | 命中的物价版本 |

### PR_LIMIT_OCCUPY

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `BUSINESS_CHARGE_TIME` | `DATE` | 业务收费发生时间 |

| `PART_SEQ` | `NUMBER(10,0)` | 多 part 项目的部位/肿物序号 |

| --- | --- | --- |

## 6. 第一阶段范围修正

第一阶段可以暂缓复杂规则，但不能让暂缓项以错误方式上线。

如果第一阶段暂不支持以下能力：

- 同项目多部位多规则。
- 主子项目自动联动。
- 复杂面积分段加成。
- 同组项目互斥封顶。
- 多肿物、多 part 输入。

则对应历史规则不得迁入新引擎自动收费。只能：

1. 保持旧逻辑且标记 `LEGACY_EQUIVALENT`。
2. 或标记 `MANUAL_REVIEW`。
3. 或暂不上线该项目。

禁止把复杂历史规则简化成单项目单规则后上线。

## 7. 必须新增的验收用例

### 用例 1：confirm 超时重试不重复占额

同一 `businessRequestNo` 第一次 confirm 超时，第二次用相同业务号重试。期望返回同一 `traceId`，占额只有一份。

### 用例 2：同一请求号参数变化被拒绝

同一 `businessRequestNo`，第二次修改 `bodyPartCode` 或 `extraParams.area`。期望返回 `IDEMPOTENT_CONFLICT`。

### 用例 3：2 小时窗口跨 3 个小时桶

10:01 收费，窗口覆盖 08:01-10:01。08:30 已收费记录必须参与累计，并发 confirm 不得突破上限。

### 用例 4：补缴费按业务时间进入窗口

12:00 补录一笔业务时间为 09:30 的收费。应按 09:30 参与规则生效和 2 小时窗口，而不是按 12:00。

### 用例 5：公式项目仍执行同手术封顶

同一手术下公式计价项目多次收费，配置同手术封顶。期望公式先算，再执行同手术封顶。

### 用例 6：批量试算同胎次互斥

同一批次录入两个同胎次项目，上限 1 个。期望第二项在 batch 结果中被折价，不允许两个都显示可收费。

### 用例 7：多肿物单独封顶后汇总

同一项目两个肿物，不同面积和部位。期望每个 `partSeq` 单独换算、单独封顶，再汇总。

### 用例 8：权威单价不一致

渠道传入单价与物价主数据不一致。confirm 必须返回 `PRICE_MISMATCH`。

### 用例 9：规则重叠发布被阻断

同一项目、同一场景、同一部位发布两个同优先级 `CONVERT_QTY`。期望发布失败。

### 用例 10：主子项目原子 cancel

主项目写 HIS 成功，子项目写 HIS 失败。HIS 必须 cancel 整组，计价中心主子明细全部变为 `CANCELLED`。

### 用例 11：部分退费不能超过原占用

原收费数量 3，已部分退费 2，再退 2。期望第二次退费被拒绝。

### 用例 12：非等价旧逻辑项目禁止普通计价回滚

特殊项目 `rollbackMode = NEW_SERVICE_ONLY`，全局开关关闭。期望渠道不得按普通价格收费，应提示转人工或暂停。

## 8. 编码前检查清单

- [ ] confirm 使用稳定 `businessRequestNo`，不是每次 HTTP 调用随机 GUID。
- [ ] `REQUEST_FINGERPRINT` 覆盖 `extraParams` 和 `pricingParts`。
- [ ] 2 小时窗口按 `BUSINESS_CHARGE_TIME` 查询。
- [ ] TIME_WINDOW 锁定窗口覆盖的全部小时桶。
- [ ] 请求、占额、折价明细状态同事务更新。
- [ ] commit 与 expire 逐笔加锁处理。
- [ ] 公式项目不再代码层跳过所有数量限制。
- [ ] batch-simulate 使用 `BatchPricingContext`。
- [ ] 多肿物、多部位项目支持 `pricingParts`。
- [ ] 单价由计价中心读取或强校验。
- [ ] 发布前做规则重叠和冲突校验。
- [ ] 主子项目按 `resultGroupNo` 原子 commit/cancel。
- [ ] 每个特殊项目配置 `rollbackMode`。
- [ ] 资金动作 `ON_ERROR` 默认 STOP。
- [ ] 本文 12 个验收用例全部纳入测试。

## 9. 结论

统一计价规则中心可以继续推进，但本文列出的约束必须作为编码前置条件。

收费系统宁可把一笔复杂项目拦下来转人工，也不能用简化模型自动算错钱。
