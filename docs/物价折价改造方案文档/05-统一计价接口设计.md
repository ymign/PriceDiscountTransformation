# 统一计价接口设计

## 1. 文档目的

本文设计统一计价规则中心对外接口，目标是让 HIS、自助机服务、微信公众号服务都通过同一套接口完成计价、折价、试算、确认和追溯。

技术前提：

- 后端：`.NET 6`
- 数据库：`Oracle 11g`
- ORM：`SqlSugarCore`
- 接口风格：`ASP.NET Core Web API`

## 2. 接口设计目标

接口必须满足以下要求：

- 所有渠道统一调用。
- 支持试算和确认分离。
- 支持规则版本追溯。
- 支持折价过程留痕。
- 支持复杂扩展参数。
- 支持后续新增规则类型时接口尽量不变。

## 3. 核心原则

### 3.1 渠道只传参数，不自己算规则

HIS、自助机、公众号只负责传入：

- 患者信息。
- 就诊信息。
- 项目信息。
- 数量单位。
- 部位。
- 收费场景。
- 操作人。

统一计价服务负责：

- 查规则。
- 匹配规则。
- 换算数量。
- 执行公式。
- 应用上下限。
- 生成折价结果。
- 写追溯日志。

### 3.2 试算和确认必须分开

试算用于页面展示，不进入最终收费结果。

确认用于正式收费，必须写入正式折价明细。

### 3.3 接口要保留扩展参数

国家规则变化不稳定，接口不能每新增一个字段就改一次所有渠道。

因此请求中必须保留：

- `ExtraParams`

用于承载暂时不能结构化的扩展参数。

但高频字段仍应结构化，例如：

- `PatientId`
- `ItemCode`
- `InputQty`
- `ChargeTime`

## 4. 接口清单

## 4.1 试算接口

接口：

`POST /api/pricing/calculate/simulate`

用途：

- 收费录入过程中实时计算。
- 不写最终折价结果。
- 可以写请求日志和步骤日志，标识为 `SIMULATE`。

## 4.2 确认计价接口

接口：

`POST /api/pricing/calculate/confirm`

用途：

- 正式收费确认前调用。
- 返回最终可落账结果。
- 写入正式折价结果明细。

## 4.3 冲正接口

接口：

`POST /api/pricing/calculate/reverse`

用途：

- 退费、作废、撤销时调用。
- 记录冲正信息。
- 根据业务口径决定是否释放累计额度。

## 4.4 提交落账接口

接口：

`POST /api/pricing/calculate/commit`

用途：

- HIS 或其他渠道收费明细落账成功后调用。
- 将确认计价产生的限额占用从 `PENDING` 改为 `CONFIRMED`。

## 4.5 取消确认接口

接口：

`POST /api/pricing/calculate/cancel`

用途：

- HIS 写收费明细失败、操作员取消、支付失败时调用。
- 释放确认计价时产生的待确认占用。

## 4.6 规则查询接口

接口：

`GET /api/pricing/rules/effective?itemCode={itemCode}&chargeTime={chargeTime}`

用途：

- 查询某项目在某个时间点的生效规则。

## 4.7 特殊项目标识查询接口

接口：

`GET /api/pricing/items/{itemCode}/special-flag`

用途：

- 渠道判断项目是否必须调用统一计价服务。
- 特殊项目在计价服务异常时不允许渠道自行按普通价格收费。

## 4.8 追溯查询接口

接口：

`POST /api/pricing/trace/query`

用途：

- 查询某患者、某收费单、某项目的计价过程与折价原因。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `requestNo` | 是 | 调用方请求流水号，必须幂等 |
| `sourceSystem` | 是 | HIS、SELF_MACHINE、WECHAT |
| `sourceTerminal` | 否 | 终端、服务或站点标识 |
| `callType` | 是 | SIMULATE、CONFIRM、REVERSE |
| `chargeScene` | 是 | 收费场景 |
| `patientId` | 是 | 患者 ID |
| `visitId` | 否 | 就诊 ID |
| `encounterNo` | 否 | 门诊号、住院号或就诊流水 |
| `chargeNo` | 确认时建议必填 | 收费单号 |
| `chargeDetailNo` | 确认时建议必填 | 收费明细号 |
| `itemCode` | 是 | 项目编码 |
| `itemName` | 是 | 项目名称 |
| `unitPrice` | 是 | 单价 |
| `inputQty` | 是 | 原始录入数量 |
| `inputUnit` | 否 | 原始录入单位 |
| `bodyPartCode` | 否 | 部位编码 |
| `chargeTime` | 是 | 计价发生时间 |
| `operatorId` | 是 | 操作人 |
| `extraParams` | 否 | 扩展参数 |

## 9. 扩展参数设计

`extraParams` 不能成为垃圾桶，必须有约束。

建议约定常用键：

| 参数 | 说明 |
| --- | --- |
| `operationNo` | 手术号 |
| `pregnancyNo` | 胎次号 |
| `age` | 年龄 |
| `isChild` | 是否儿童 |
| `area` | 面积 |
| `areaUnit` | 面积单位 |
| `length` | 长度 |
| `lengthUnit` | 长度单位 |
| `distance` | 距离 |
| `distanceUnit` | 距离单位 |
| `mainChargeDetailNo` | 主项目收费明细号 |

如果某个扩展参数变成高频查询条件，应升级为结构化字段。

## 10. 幂等设计

确认计价接口必须幂等。

幂等键建议：

- `sourceSystem + requestNo`

处理逻辑：

- 如果同一请求号重复确认，直接返回第一次结果。
- 不允许重复写折价结果明细。
- 请求参数不一致时返回错误，提示请求号冲突。

## 10.1 确认、提交、取消状态

确认计价不应直接等同于 HIS 落账完成。

建议状态：

| 状态 | 说明 |
| --- | --- |
| `CONFIRM_PENDING` | 已确认计价，等待业务系统落账 |
| `CONFIRMED` | 业务系统落账成功 |
| `CANCELLED` | 业务系统落账失败或取消 |
| `REVERSED` | 已退费或冲正 |

处理流程：

1. 调用 `confirm`，计算金额并占用额度。
2. HIS 或渠道写本地收费明细。
3. 写入成功后调用 `commit`。
4. 写入失败、支付失败或操作取消后调用 `cancel`。

后台应定时扫描长时间停留在 `CONFIRM_PENDING` 的记录，按业务策略取消或人工处理。

## 11. 试算与确认处理差异

### 11.1 试算

试算应：

- 记录请求日志。
- 可记录步骤日志。
- 不写正式折价结果明细。
- 不占用累计额度。

### 11.2 确认

确认应：

- 记录请求日志。
- 记录步骤日志。
- 写待确认折价结果明细。
- 占用累计额度。
- 等业务系统 `commit` 后转为正式确认。

### 11.3 冲正

冲正应：

- 记录冲正日志。
- 关联原确认请求。
- 根据规则口径决定是否释放累计额度。

## 12. 统一计价处理流程

建议服务内部流程：

1. 校验请求参数。
2. 校验幂等。
3. 写入计价请求日志。
4. 查询项目当前生效规则。
5. 按规则优先级匹配条件。
6. 按动作顺序执行。
7. 记录每个步骤输入输出。
8. 生成最终金额。
9. 生成折价原因说明。
10. 如果是确认请求，在事务中锁定限额维度并占用额度。
11. 如果是确认请求，写入待确认折价结果明细。
12. 返回计价结果。

## 13. 规则执行器设计

为保证扩展性，建议后端实现以下接口思想。

### 13.1 条件执行器

```csharp
public interface IRuleConditionEvaluator
{
    string ConditionType { get; }

    Task<bool> IsMatchAsync(PricingContext context, RuleCondition condition);
}
```

用途：

- 按条件类型判断规则是否命中。

### 13.2 动作执行器

```csharp
public interface IRuleActionExecutor
{
    string ActionType { get; }

    Task ExecuteAsync(PricingContext context, RuleAction action);
}
```

用途：

- 按动作类型执行换算、公式、封顶、折价等处理。

### 13.3 公式执行器

```csharp
public interface IPricingFormulaExecutor
{
    string FormulaCode { get; }

    Task<decimal> CalculateAsync(PricingContext context, FormulaDefinition formula, decimal quantity);
}
```

用途：

- 公式类型新增时，只新增执行器，不改 HIS、自助机、公众号。

## 15. 追溯查询接口

接口：

`POST /api/pricing/trace/query`

请求：

```json
{
  "patientId": "P001",
  "chargeNo": "C000001",
  "itemCode": "CT001",
  "dateFrom": "2026-05-01",
  "dateTo": "2026-05-07"
}
```

响应重点：

```json
{
  "success": true,
  "items": [
    {
      "traceId": "TR202605070001",
      "chargeNo": "C000001",
      "itemCode": "CT001",
      "itemName": "CT平扫",
      "ruleCode": "RULE_CT_2H_LIMIT",
      "ruleVersion": 3,
      "originalAmount": 1200,
      "finalAmount": 900,
      "discountAmount": 300,
      "reasonDesc": "2小时内收费上限3，本次录入4，超出1个折价为0元。"
    }
  ]

```

## 16. 错误码建议

| 错误码 | 说明 |
| --- | --- |
| `INVALID_REQUEST` | 请求参数不合法 |
| `IDEMPOTENT_CONFLICT` | 请求号重复但参数不一致 |
| `RULE_NOT_FOUND` | 未找到规则 |
| `RULE_MATCH_FAILED` | 找到规则但条件不匹配 |
| `FORMULA_NOT_SUPPORTED` | 公式未支持 |
| `ACTION_NOT_SUPPORTED` | 动作未支持 |
| `CALCULATION_FAILED` | 计算失败 |
| `REVERSE_TARGET_NOT_FOUND` | 冲正原记录不存在 |

## 17. 接入改造要求

### 17.1 HIS

- HIS 负责采集完整参数。
- HIS 不再新增本地折价逻辑。
- HIS 确认收费前调用 `confirm`。

### 17.2 自助机

- 自助机服务调用 `simulate` 展示价格。
- 支付前调用 `confirm` 锁定计价结果。

### 17.3 微信公众号

- 公众号服务调用 `simulate` 展示价格。
- 用户确认支付前调用 `confirm`。

## 18. 结论

接口设计的核心不是多做几个接口，而是统一规则执行边界。

以后国家规则再乱，只要新增：

- 条件执行器。
- 动作执行器。
- 公式执行器。
- 规则配置。

就可以让 HIS、自助机、公众号共用同一套结果，避免各端反复改代码。
