# 统一计价接口设计

## 1. 文档目的

本文设计统一计价规则中心对外接口，目标是让 HIS、自助机服务、微信公众号服务都通过同一套接口完成计价、折价、试算、确认和追溯。

技术前提：

- 后端：`.NET 6`
- 数据库：`Oracle 11g`
- ORM：`SqlSugarCore`
- 接口风格：`ASP.NET Core Web API`

## 2. 接口设计目标

接口必须满足以下要求：

- 所有渠道统一调用。
- 支持试算和确认分离。
- 支持规则版本追溯。
- 支持折价过程留痕。
- 支持复杂扩展参数。
- 支持后续新增规则类型时接口尽量不变。

## 3. 核心原则

### 3.1 渠道只传参数，不自己算规则

HIS、自助机、公众号只负责传入：

- 患者信息。
- 就诊信息。
- 项目信息。
- 数量单位。
- 部位。
- 收费场景。
- 操作人。

统一计价服务负责：

- 查规则。
- 匹配规则。
- 换算数量。
- 执行公式。
- 应用上下限。
- 生成折价结果。
- 写追溯日志。

### 3.2 试算和确认必须分开

试算用于页面展示，不进入最终收费结果。

确认用于正式收费，必须写入正式折价明细。

### 3.3 接口要保留扩展参数

国家规则变化不稳定，接口不能每新增一个字段就改一次所有渠道。

因此请求中必须保留：

- `ExtraParams`

用于承载暂时不能结构化的扩展参数。

但高频字段仍应结构化，例如：

- `PatientId`
- `BusinessChargeTime`
- `Items[].ItemCode`
- `Items[].InputQty`

## 4. 接口清单

## 4.1 试算接口

接口：

`POST /api/pricing/calculate/simulate`

用途：

- 收费录入过程中实时计算。
- 不写最终折价结果。
- 可以写请求日志和步骤日志，标识为 `SIMULATE`。

## 4.2 确认计价接口

接口：

`POST /api/pricing/calculate/confirm`

用途：

- 正式收费确认前调用。
- 返回最终可落账结果。
- 写入正式折价结果明细。

## 4.3 冲正接口

接口：

`POST /api/pricing/calculate/reverse`

用途：

- 退费、作废、撤销时调用。
- 记录冲正信息。
- 根据业务口径决定是否释放累计额度。

## 4.4 提交落账接口

接口：

`POST /api/pricing/calculate/commit`

用途：

- HIS 或其他渠道收费明细落账成功后调用。
- 将确认计价产生的限额占用从 `PENDING` 改为 `CONFIRMED`。
- 必须回传 HIS 真实落账明细 `actualItems`，计价中心用 confirm 保存的结果逐项对账后才允许推进状态。

## 4.5 取消确认接口

接口：

`POST /api/pricing/calculate/cancel`

用途：

- HIS 写收费明细失败、操作员取消、支付失败时调用。
- 释放确认计价时产生的待确认占用。

## 4.6 规则查询接口

接口：

`GET /api/pricing/rules/effective?itemCode={itemCode}&chargeTime={chargeTime}`

用途：

- 查询某项目在某个时间点的生效规则。

## 4.7 特殊项目标识查询接口

接口：

`GET /api/pricing/items/{itemCode}/special-flag`

用途：

- 渠道判断项目是否必须调用统一计价服务。
- 特殊项目在计价服务异常时不允许渠道自行按普通价格收费。

## 4.8 追溯查询接口

接口：

`POST /api/pricing/trace/query`

用途：

- 查询某患者、某收费单、某项目的计价过程与折价原因。

## 4.9 批量试算接口

接口：

`POST /api/pricing/calculate/batch-simulate`

用途：

- 收费录入时一次性录入多个项目，批量试算。
- 返回结果按项目独立展示，但计算必须共享同批上下文，支持同批内同组互斥、同胎次封顶、同手术封顶和同项目多行累计。
- 不占额度，与单笔 simulate 行为一致。

## 6. 请求字段说明

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `requestNo` | 否 | 调用方技术请求流水号，用于排查一次 HTTP 调用；不是 confirm 幂等键 |
| `businessRequestNo` | 确认时必填 | 调用方稳定业务号，重试必须复用 |
| `sourceSystem` | 是 | HIS、SELF_MACHINE、WECHAT |
| `sourceTerminal` | 否 | 终端、服务或站点标识 |
| `chargeScene` | 否 | 收费场景 |
| `patientId` | 是 | 患者 ID |
| `visitId` | 否 | 就诊 ID |
| `visitType` | 否 | 就诊类型，用于 VISIT_TYPE_MATCH |
| `patientAge` | 否 | 患者年龄，用于 AGE_MATCH |
| `encounterNo` | 否 | 门诊号、住院号或就诊流水 |
| `chargeNo` | 确认时建议必填 | 收费单号 |
| `businessChargeTime` | 是 | 业务收费发生时间，是规则生效、日限额和时间窗判断的时间基准 |
| `operatorId` | 否 | 操作人 |
| `extraParams` | 否 | 结算级扩展参数 |
| `items` | 是 | 费用明细集合，一次结算可包含多条费用 |

费用明细字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `itemRequestNo` | 否 | 调用方单条费用请求号，用于响应行关联 |
| `chargeDetailNo` | 确认时建议必填 | 收费明细号 |
| `itemCode` | 是 | 项目编码 |
| `itemName` | 否 | 项目名称 |
| `itemGroupCode` | 否 | 项目组编码，用于同组互斥、同手术封顶等组规则 |
| `unitPrice` | 是 | 单价；服务端要求不能小于 0，confirm 时应与权威物价校验 |
| `inputQty` | 是 | 原始录入数量；服务端要求大于 0 |
| `unit` | 否 | 原始录入单位 |
| `bodyPartCode` | 否 | 部位编码 |
| `businessChargeTime` | 否 | 单条费用计价发生时间；为空时使用结算级 `businessChargeTime` |
| `extraParams` | 否 | 单条费用扩展参数 |
| `pricingParts` | 复杂项目必填 | 多肿物、多部位、多面积明细；传入时每个片段 `qty` 必须大于 0 |

建议约定常用键：

| 参数 | 说明 |
| --- | --- |
| `operationNo` | 手术号 |
| `pregnancyNo` | 胎次号 |
| `isChild` | 是否儿童 |
| `area` | 面积 |
| `areaUnit` | 面积单位 |
| `length` | 长度 |
| `lengthUnit` | 长度单位 |

| `distanceUnit` | 距离单位 |

如果某个扩展参数变成高频查询条件，应升级为结构化字段。

## 10. 幂等设计

确认计价接口必须幂等。

幂等键建议：

- `sourceSystem + businessRequestNo + callType`

说明：

- `requestNo` 是技术请求流水，可以每次调用不同。
- `businessRequestNo` 是业务确认流水，必须稳定映射到一次收费确认动作。
- `callType` 由接口路由决定，例如 `/calculate/confirm` 在服务端记为 `CONFIRM`，不是请求 JSON 里的字段。
- confirm 超时重试必须复用同一个 `businessRequestNo`，不能重新生成随机 GUID。

处理逻辑：

1. 收到请求，检查 `sourceSystem + businessRequestNo + callType` 是否已存在
2. 如果不存在：正常处理，写入请求日志
3. 如果存在：
   a. 比对规范化后的 `REQUEST_FINGERPRINT`
   b. 参数一致：直接返回上次的结果（从 PR_CHARGE_REQUEST_LOG.RESPONSE_JSON 读取）
   c. 参数不一致：返回 IDEMPOTENT_CONFLICT 错误

`REQUEST_FINGERPRINT` 至少覆盖：

- `patientId`、`visitId`、`visitType`、`patientAge`、`encounterNo`
- `chargeScene`、`chargeNo`、结算级 `businessChargeTime`
- `items` 全量规范化 JSON，包括每条费用的 `chargeDetailNo`、`itemCode`、`itemGroupCode`、`inputQty`、`unit`、`unitPrice`、`bodyPartCode`、单条 `businessChargeTime`
- 结算级和费用明细级 `operationNo`、`pregnancyNo`、`mainChargeDetailNo`
- 结算级和费用明细级 `extraParams` 全量规范化 JSON
- 费用明细级 `pricingParts` 全量规范化 JSON
- `unitPrice` 或计价中心确认的权威物价版本

IDEMPOTENT_CONFLICT 响应：
```json
{
  "success": false,
  "errorCode": "IDEMPOTENT_CONFLICT",
  "errorMessage": "业务请求号 BR001 已被使用，但本次请求参数与首次 confirm 不一致。请核对业务号或重新发起收费动作。",
  "originalRequestAt": "2026-05-07T10:30:00",
  "originalTraceId": "TR202605070001"
}
```

约束：
- 不允许覆盖已有请求的结果
- IDEMPOTENT_CONFLICT 只在 confirm 和 reverse 接口校验
- simulate 接口不校验幂等（试算可以重复）

## 10.1 确认、提交、取消状态

确认计价不应直接等同于 HIS 落账完成。

建议状态：

| 状态 | 说明 |
| --- | --- |
| `CONFIRM_PENDING` | 已确认计价，等待业务系统落账 |
| `CONFIRMED` | 业务系统落账成功 |
| `CANCELLED` | 业务系统落账失败或取消 |
| `EXPIRED` | 确认结果超时释放 |
| `REVERSED` | 已退费或冲正 |

处理流程：

1. 调用 `confirm`，计算金额并占用额度。
2. HIS 或渠道写本地收费明细。
3. 写入成功后调用 `commit`。
4. 写入失败、支付失败或操作取消后调用 `cancel`。

后台应定时扫描长时间停留在 `CONFIRM_PENDING` 的记录，按业务策略取消或人工处理。

状态必须同时体现在请求日志、限额占用和折价结果明细中。`commit`、`cancel`、`expire` 更新三类记录时必须在同一事务内完成。

### business_request_no 口径

不同接口对 `business_request_no` 的语义不同，HIS 不能混用：

| 接口 | 定位/幂等字段 | 说明 |
| --- | --- | --- |
| `special-flags` | 无幂等要求 | `business_request_no` 可选，仅用于诊断和串联日志。 |
| `simulate` / `batch-simulate` | `source_system + business_request_no + SIMULATE` | `business_request_no` 可选；如果传入，必须保证每次试算唯一，重复返回 409 `BUSINESS_REQUEST_NO_DUPLICATED`。 |
| `confirm` | `source_system + business_request_no + CONFIRM` | `business_request_no` 必填且必须稳定，超时重试必须复用；参数不一致返回 `IDEMPOTENT_CONFLICT`。 |
| `commit` | `request_id` | 使用 confirm 响应返回的 `request_id`，不使用 `business_request_no` 定位。 |
| `cancel` | `request_id` | 使用 confirm 响应返回的 `request_id`，不使用 `business_request_no` 定位。 |
| `reverse` | `original_request_id + reverse_no` | 同一退费/冲正流水重试必须复用 `reverse_no`；参数不一致返回 `IDEMPOTENT_CONFLICT`。 |

`commit` 请求必须包含：

- `requestId`：confirm 响应返回的请求 ID。
- `chargeNo`：HIS 实际收费单号。
- `actualTotalAmount`：HIS 实际落账总金额。
- `actualItems[]`：HIS 已经写库成功的真实收费明细。

`actualItems[]` 对账规则：

- 普通项目和主项目按 `chargeDetailNo + itemCode + partSeq` 严格匹配，并校验数量、金额。
- 替换子项和加收子项允许 HIS 落账时生成新的 `chargeDetailNo`，但必须按 `itemCode + partSeq + finalQty + finalAmount` 匹配。
- HIS 多回传或少回传任一有效收费明细，均视为 `COMMIT_DETAIL_MISMATCH`。
- 金额或数量不一致分别返回 `COMMIT_AMOUNT_MISMATCH`、`COMMIT_QTY_MISMATCH`。

### confirm 结果有效期

confirm 响应中增加 `expireAt` 字段：

```json
{
  "traceId": "TR202605070001",
  "finalAmount": 900,
  "expireAt": "2026-05-07T11:00:00",
  "expireSeconds": 1800
}
```

规则：
1. 默认 30 分钟（可配置）
2. 超过有效期后，后台任务自动将占用标记为 EXPIRED 并释放额度
3. HIS 必须在有效期内完成落账并调 commit
4. 超过有效期后调 commit 返回 EXPIRED 错误，HIS 需重新 confirm

超时清理任务（每5分钟）：
```sql
-- 禁止只用一条批量 UPDATE 直接过期所有记录。
-- 清理任务必须逐笔锁定请求，确认未收到 commit 且 HIS 未落账后，
-- 再将请求日志、限额占用、折价明细同事务更新为 EXPIRED。
```

按渠道设置不同超时：
| 来源系统 | 超时时间 | 说明 |
|---|---|---|
| HIS | 30 分钟 | HIS 可能有审批步骤 |
| SELF_MACHINE | 10 分钟 | 自助机流程简单 |
| WECHAT | 15 分钟 | 用户可能犹豫 |

## 11. 试算与确认处理差异

### 11.1 试算

试算应：

- 记录请求日志。
- 可记录步骤日志。
- 不写正式折价结果明细。
- 不占用累计额度。

### 11.2 确认

确认应：

- 记录请求日志。
- 记录步骤日志。
- 写本次响应中所有可落账费用明细的待确认折价结果，包含普通明细、特殊明细、替换子项和加收子项。
- 仅对命中特殊规则且需要保护额度的结果写 `PENDING` 限额占用；普通明细只作为 commit 对账基准。
- 等业务系统 `commit` 后转为正式确认。

### 11.3 冲正

冲正应：

- 记录冲正日志。
- 关联原确认请求。
- 根据规则口径决定是否释放累计额度。
- 如果命中的原收费明细带 `resultGroupNo`，应把同组主项目、替换子项、加收子项一并纳入退费数量和金额校验，避免只退主项目、子项残留。

## 12. 统一计价处理流程

建议服务内部流程：

1. 校验请求参数。
2. 校验幂等。
3. 写入计价请求日志。
4. 查询项目当前生效规则。
5. 按规则优先级匹配条件。
6. 按动作顺序执行。
7. 记录每个步骤输入输出。
8. 生成最终金额。
9. 生成折价原因说明。
10. 如果是确认请求，在事务中锁定限额维度并占用额度。
11. 如果是确认请求，写入待确认折价结果明细。
12. 返回计价结果。

## 13. 规则执行器设计

为保证扩展性，建议后端实现以下接口思想。

### 13.1 条件执行器

```csharp
public interface IRuleConditionEvaluator
{
    string ConditionType { get; }

    Task<bool> IsMatchAsync(PricingContext context, RuleCondition condition);
}
```

用途：

- 按条件类型判断规则是否命中。

### 13.2 动作执行器

```csharp
public interface IRuleActionExecutor
{
    string ActionType { get; }

    Task ExecuteAsync(PricingContext context, RuleAction action);
}
```

用途：

- 按动作类型执行换算、公式、封顶、折价等处理。

### 13.3 公式执行器

```csharp
public interface IPricingFormulaExecutor
{
    string FormulaCode { get; }

    Task<decimal> CalculateAsync(PricingContext context, FormulaDefinition formula, decimal quantity);
}
```

用途：

- 公式类型新增时，只新增执行器，不改 HIS、自助机、公众号。

## 17. 超时与降级策略

### 超时阈值

| 接口 | 超时阈值 | 说明 |
|---|---|---|
| simulate | 3 秒 | 试算允许宽松 |
| confirm | 5 秒 | 确认需要更可靠 |
| commit/cancel | 2 秒 | 简单状态更新 |
| special-flag | 1 秒 | 轻量查询，必须快 |
| batch-simulate | 10 秒 | 按项目数量动态调整 |

### 降级策略

special-flag 接口：
- 超时或异常时返回 `{"special": true}`
- 宁可多调一次计价服务，不能漏掉特殊项目

simulate 接口：
- 超时后渠道不展示价格，提示"价格计算中，请稍候"
- 不允许按默认单价展示

confirm 接口：
- 超时后不允许收费
- 提示"计价服务暂时不可用，请稍后重试"

### 熔断机制（渠道侧）

1. 连续 5 次调用失败或超时，触发熔断
2. 熔断期间（30秒），直接返回 SERVICE_UNAVAILABLE
3. 30秒后进入半开状态，允许 1 次试探请求
4. 试探成功则恢复，失败则继续熔断

### 特殊项目降级规则

特殊项目（special-flag = true）在计价服务异常时：
- 不允许渠道自行按普通价格收费
- 必须提示稍后再试或转人工窗口
- 这是强制约束，不是建议

## 18. 接口 SLA 定义

| 接口 | P50 延迟 | P99 延迟 | 成功率目标 |
|---|---|---|---|
| simulate | ≤200ms | ≤1s | ≥99.9% |
| confirm | ≤300ms | ≤2s | ≥99.95% |
| commit | ≤100ms | ≤500ms | ≥99.99% |
| cancel | ≤100ms | ≤500ms | ≥99.99% |
| special-flag | ≤50ms | ≤200ms | ≥99.99% |
| batch-simulate | ≤500ms | ≤5s | ≥99.9% |

报警规则：
- confirm 成功率 <99.9% 持续 5 分钟 → P1 立即处理
- confirm P99 延迟 >3s 持续 5 分钟 → P2 30分钟内处理
- 熔断触发次数 >10次/小时 → P1
- CONFIRM_PENDING 超时数 >50条/小时 → P1

## 20. 接入改造要求

### 20.1 HIS

- HIS 负责采集完整参数。
- HIS 不再新增本地折价逻辑。
- HIS 确认收费前调用 `confirm`。

### 20.2 自助机

- 自助机服务调用 `simulate` 展示价格。
- 支付前调用 `confirm` 锁定计价结果。

### 20.3 微信公众号

- 公众号服务调用 `simulate` 展示价格。
- 用户确认支付前调用 `confirm`。

## 21. 结论

接口设计的核心不是多做几个接口，而是统一规则执行边界。

以后国家规则再乱，只要新增：

- 条件执行器。
- 动作执行器。
- 公式执行器。
- 规则配置。

就可以让 HIS、自助机、公众号共用同一套结果，避免各端反复改代码。
