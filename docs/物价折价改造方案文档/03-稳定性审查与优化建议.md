# 稳定性审查与优化建议

## 1. 审查结论

当前方案的大方向是正确的：

- 规则集中维护。
- 统一计价服务。
- 多渠道统一调用。
- 规则版本化。
- 折价过程留痕。
- 条件、动作、公式执行器扩展。

但从“收费出错就是钱”的角度看，目前还需要补强几类稳定性能力。

最关键的不是再多设计几个字段，而是要保证：

1. 同一个患者同一个项目在多端并发收费时不会突破上限。
2. 计价成功但 HIS 落账失败时不会污染累计额度。
3. 规则变更不能随便保存即生效，必须审批、发布、回滚。
4. 金额、数量、取整、四舍五入必须有统一口径。
5. 自助机、微信公众号不能在计价服务异常时自己兜底乱算。
6. 每次确认收费必须能和 HIS 收费明细一一对应。
7. 退费、作废、冲正必须影响后续累计口径。

## 2. 当前最需要补强的稳定性点

## 2.1 并发占额问题

### 风险

需求明确“上下限数量、金额为全院限制”，门诊和住院都要一起算。

如果 HIS、自助机、公众号同时给同一个患者、同一个项目收费，就会出现并发问题。

示例：

- 单日上限 3 次。
- 患者当前已收费 2 次。
- HIS 和自助机同时各提交 1 次。
- 两边都查到“还剩 1 次”。
- 两边都成功收费。
- 最终收了 4 次，突破上限。

### 优化建议

必须引入“确认计价占额”机制。

建议新增：

- `PR_LIMIT_OCCUPY`

确认计价时先占用额度，HIS 落账成功后标记为已确认，落账失败后释放或作废。

### 关键原则

- 试算不占额度。
- 确认必须占额度。
- 退费或作废必须冲正额度。
- 占额和写折价结果要在同一事务里完成。

## 2.2 确认计价和 HIS 落账一致性

### 风险

统一计价服务确认成功后，HIS 还要写收费明细。

如果出现：

- 计价服务确认成功。
- HIS 写收费明细失败。

那么计价中心可能已经认为额度被占用了，但 HIS 实际没有收费。

### 优化建议

确认接口不要直接等同于最终落账完成。

建议分状态：

- `CONFIRM_PENDING`：计价确认，等待 HIS 落账。
- `CONFIRMED`：HIS 落账成功。
- `CANCELLED`：HIS 落账失败或取消。
- `REVERSED`：已退费或冲正。

建议增加接口：

- `POST /api/pricing/calculate/commit`
- `POST /api/pricing/calculate/cancel`

处理流程：

1. HIS 调 `confirm` 获取计价结果并占额。
2. HIS 写本地收费明细。
3. HIS 写入成功后调 `commit`。
4. HIS 写入失败后调 `cancel`。

如果 HIS 很难改成三段式，至少要有后台补偿任务扫描长时间 `CONFIRM_PENDING` 的记录。

## 2.3 规则发布审批问题

### 风险

物价规则一旦错配，会直接影响收费。

如果业务人员保存后立刻生效，风险很高。

### 优化建议

规则生命周期必须拆成：

- 草稿。
- 待审核。
- 已审核。
- 已发布。
- 已停用。
- 已回滚。

至少要求：

- 修改规则只生成草稿。
- 审核后才能发布。
- 发布时生成新版本。
- 历史版本不能物理删除。
- 回滚只能回滚到已发布版本。

## 2.4 规则模拟验证问题

### 风险

规则配置没问题，不代表结果一定正确。

尤其是：

- 单位换算。
- 金额上下限。
- 同组互斥。
- 2 小时窗口。
- 同一手术封顶。
- 儿童加收。

这些都很容易因配置错误导致错账。

### 优化建议

发布规则前必须支持“规则模拟验证”。

建议每条规则配置一组测试样本：

- 输入参数。
- 期望金额。
- 期望折价金额。
- 期望原因。

发布前自动跑样本，不通过不能发布。

建议新增：

- `PR_RULE_TEST_CASE`
- `PR_RULE_TEST_RUN`

## 2.5 金额和数量取整口径

### 风险

PPT 中明确出现：

- 封顶数量按小数点后一位取舍取整。
- 不足基础计价量按 1 个数量收。
- 大于 1 小于 2，按 2 个收。

如果不同公式自己处理取整，会造成多端和多规则不一致。

### 优化建议

必须把取整策略配置化并统一执行。

建议规则动作参数支持：

- `roundMode`
- `roundScale`
- `minChargeQty`
- `ceilBaseQty`

常见策略：

- 向上取整。
- 四舍五入。
- 保留 1 位。
- 保留 2 位。
- 不足按 1 收。
- 超过基础计价量按下一个单位收。

## 2.6 字段为空不校验的精确定义

### 风险

需求写了“字段若不填写，则不校验”。

但数据库里会出现三种状态：

- `NULL`
- `0`
- 空字符串

如果不统一，可能出现把 0 当不校验，或把空当 0 的问题。

### 优化建议

必须明确：

- `NULL` 表示不启用该限制。
- `0` 表示限制为 0，通常不允许配置，除非业务明确需要。
- 前端空值入库必须为 `NULL`。

前后端都要校验。

## 2.7 规则优先级与冲突

### 风险

一个项目可能同时命中：

- 金额上限。
- 数量上限。
- 公式计价。
- 2 小时窗口。
- 儿童加收。
- 同一手术封顶。

如果规则执行顺序不稳定，会导致同样输入算出不同结果。

### 优化建议

必须定义全局执行顺序。

建议顺序：

1. 项目和场景匹配。
2. 部位和单位匹配。
3. 数量换算。
4. 公式计价。
5. 金额下限。
6. 金额上限。
7. 数量上限。
8. 时间窗口上限。
9. 同组互斥或同一手术封顶。
10. 加收子项目。
11. 最终折价明细生成。

如果某条规则需要特殊顺序，必须显式配置动作排序，并记录到追溯日志。

## 2.8 服务异常时的渠道处理

### 风险

如果统一计价服务异常，自助机或公众号为了不影响收费，可能自己按普通单价收费。

这会直接绕过规则中心。

### 优化建议

对于特殊项目：

- 计价服务不可用时，不允许渠道自行收费。
- 必须提示稍后再试或转人工窗口。

对于普通项目：

- 可按原普通逻辑处理，但必须确保项目未启用特殊规则。

建议提供轻量接口：

- `GET /api/pricing/items/{itemCode}/special-flag`

用于渠道快速判断是否特殊项目。

## 2.9 缓存失效与规则生效时间

### 风险

如果规则中心加缓存，发布新规则后缓存没刷新，会导致新旧规则混用。

### 优化建议

规则缓存必须满足：

- 只缓存已发布规则。
- 发布、停用、回滚后立即失效。
- 响应中必须返回规则版本。
- 计价日志必须记录命中的规则版本。
- 支持按 `chargeTime` 查询历史生效规则，不能只查当前规则。

## 2.10 追溯日志不能只写成功结果

### 风险

失败请求如果不记录，后续无法排查为什么某端没收费、为什么提示失败。

### 优化建议

所有请求都应该记录请求日志：

- 成功。
- 失败。
- 参数错误。
- 规则冲突。
- 公式异常。
- 幂等冲突。

只有正式确认成功后才写折价结果明细。

## 3. 建议新增的数据表

## 3.1 限额占用表 `PR_LIMIT_OCCUPY`

用途：

- 防止多端并发突破全院上限。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `OCCUPY_ID` | `NUMBER(18,0)` | 主键 |
| `REQUEST_ID` | `NUMBER(18,0)` | 请求 ID |
| `TRACE_ID` | `VARCHAR2(50)` | 追踪号 |
| `PATIENT_ID` | `VARCHAR2(50)` | 患者 ID |
| `ITEM_CODE` | `VARCHAR2(50)` | 项目编码 |
| `RULE_ID` | `NUMBER(18,0)` | 规则 ID |
| `RULE_VERSION_NO` | `NUMBER(10,0)` | 规则版本 |
| `LIMIT_TYPE` | `VARCHAR2(50)` | DAY_QTY、ONCE_QTY、TIME_WINDOW、DAY_AMOUNT |
| `LIMIT_KEY` | `VARCHAR2(200)` | 限额维度键 |
| `OCCUPY_QTY` | `NUMBER(18,4)` | 占用数量 |
| `OCCUPY_AMT` | `NUMBER(18,4)` | 占用金额 |
| `STATUS` | `VARCHAR2(20)` | PENDING、CONFIRMED、CANCELLED、REVERSED、EXPIRED |
| `OCCUPIED_AT` | `DATE` | 占用时间 |
| `CONFIRMED_AT` | `DATE` | 确认时间 |
| `EXPIRE_AT` | `DATE` | 过期时间 |

建议唯一约束或索引：

- `PATIENT_ID, ITEM_CODE, LIMIT_TYPE, LIMIT_KEY, STATUS`

注意：

- Oracle 中不能只靠唯一约束解决累计上限，仍要在事务中锁定限额维度。

## 3.2 限额锁表 `PR_LIMIT_LOCK`

用途：

- 为全院累计限额提供数据库级锁定维度。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `LOCK_KEY` | `VARCHAR2(200)` | 主键 |
| `LOCK_DESC` | `VARCHAR2(500)` | 锁说明 |
| `UPDATED_AT` | `DATE` | 更新时间 |

使用方式：

- 计价确认时构造 `LOCK_KEY`。
- 例如：`DAY:P001:CT001:20260507`。
- 在事务中 `SELECT ... FOR UPDATE` 锁住该行。
- 再查询已确认和待确认占用额度。
- 再判断本次是否还能收费。

## 3.3 规则审核表 `PR_RULE_APPROVAL`

用途：

- 支持规则发布前审核。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `APPROVAL_ID` | `NUMBER(18,0)` | 主键 |
| `RULE_ID` | `NUMBER(18,0)` | 规则 ID |
| `VERSION_NO` | `NUMBER(10,0)` | 版本号 |
| `APPROVAL_STATUS` | `VARCHAR2(20)` | PENDING、APPROVED、REJECTED |
| `SUBMITTED_BY` | `VARCHAR2(50)` | 提交人 |
| `SUBMITTED_AT` | `DATE` | 提交时间 |
| `APPROVED_BY` | `VARCHAR2(50)` | 审核人 |
| `APPROVED_AT` | `DATE` | 审核时间 |
| `APPROVAL_REMARK` | `VARCHAR2(1000)` | 审核意见 |

## 3.4 规则测试用例表 `PR_RULE_TEST_CASE`

用途：

- 发布规则前进行模拟验证。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `CASE_ID` | `NUMBER(18,0)` | 主键 |
| `RULE_ID` | `NUMBER(18,0)` | 规则 ID |
| `VERSION_NO` | `NUMBER(10,0)` | 版本号 |
| `CASE_NAME` | `VARCHAR2(200)` | 用例名称 |
| `REQUEST_JSON` | `CLOB` | 测试输入 |
| `EXPECTED_JSON` | `CLOB` | 期望输出 |
| `IS_ENABLED` | `CHAR(1)` | 是否启用 |

## 3.5 规则测试运行表 `PR_RULE_TEST_RUN`

用途：

- 记录规则发布前的测试结果。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `RUN_ID` | `NUMBER(18,0)` | 主键 |
| `CASE_ID` | `NUMBER(18,0)` | 用例 ID |
| `RULE_ID` | `NUMBER(18,0)` | 规则 ID |
| `VERSION_NO` | `NUMBER(10,0)` | 版本号 |
| `RUN_STATUS` | `VARCHAR2(20)` | PASSED、FAILED |
| `ACTUAL_JSON` | `CLOB` | 实际输出 |
| `DIFF_JSON` | `CLOB` | 差异 |
| `RUN_BY` | `VARCHAR2(50)` | 执行人 |
| `RUN_AT` | `DATE` | 执行时间 |

## 4. 建议新增或调整的接口

## 4.1 提交落账接口

接口：

`POST /api/pricing/calculate/commit`

用途：

- HIS 收费明细落账成功后通知计价中心。
- 将限额占用从 `PENDING` 改为 `CONFIRMED`。

## 4.2 取消确认接口

接口：

`POST /api/pricing/calculate/cancel`

用途：

- HIS 写收费明细失败或操作员取消时释放占用。

## 4.3 特殊项目标识查询接口

接口：

`GET /api/pricing/items/{itemCode}/special-flag`

用途：

- 渠道判断服务异常时是否允许走普通收费逻辑。

## 4.4 规则模拟验证接口

接口：

`POST /api/pricing/rules/{ruleId}/versions/{versionNo}/test-run`

用途：

- 发布前运行规则测试用例。

## 4.5 规则审核接口

接口：

`POST /api/pricing/rules/{ruleId}/versions/{versionNo}/submit-approval`

接口：

`POST /api/pricing/rules/{ruleId}/versions/{versionNo}/approve`

接口：

`POST /api/pricing/rules/{ruleId}/versions/{versionNo}/reject`

## 5. 必须明确的业务口径

以下问题不确认，系统做得再漂亮也可能错账。

## 5.1 单次收费上限口径

必须确认“单次”到底指：

- 单条收费明细。
- 单次收费动作。
- 单台手术。
- 单次医嘱。
- 单次执行。

不同解释会导致完全不同的累计维度。

## 5.2 全院累计口径

必须确认累计范围：

- 门诊是否算。
- 住院是否算。
- 急诊是否算。
- 自助机是否算。
- 公众号是否算。
- 已退费记录是否算。
- 作废记录是否算。

## 5.3 同一手术口径

PPT 中提到同一手术封顶。

必须确认系统里稳定的手术标识是什么：

- 手术申请号。
- 手术安排号。
- 手术台次号。
- 医嘱号。
- 住院号 + 手术日期。

没有稳定标识就不能准确做同一手术封顶。

## 5.4 同胎次口径

规则表中有同胎次项目。

必须确认胎次来源：

- 医嘱录入。
- 检查申请。
- 产科系统。
- 人工输入。

## 5.5 退费是否释放额度

必须确认：

- 全额退费是否释放全部额度。
- 部分退费是否按数量释放。
- 隔日退费是否影响原自然日额度。
- 冲正后重新收费是否重新计算。

## 5.6 金额取整口径

必须确认：

- 中间计算保留几位。
- 最终收费保留几位。
- 折价金额保留几位。
- 四舍五入还是向上取整。
- 是否按医保接口要求保留 2 位。

## 6. 上线稳定性建议

## 6.1 灰度开关

建议至少支持：

- 按项目启用。
- 按院区启用。
- 按收费场景启用。
- 按来源系统启用。

## 6.2 双跑对账

上线初期建议：

- 新规则中心试算。
- 旧逻辑仍落账。
- 比较新旧金额差异。
- 差异确认无误后再切正式。

## 6.3 关键监控

必须监控：

- 计价接口成功率。
- 计价接口耗时。
- 规则命中率。
- 折价金额总额。
- 折价失败次数。
- 幂等冲突次数。
- 长时间 `PENDING` 占额数量。
- 新旧逻辑差异金额。

## 6.4 每日凌晨对账

建议建设每日对账任务，凌晨自动核查前一日数据。

重点核查：

- HIS 收费金额与计价中心最终金额是否一致。
- 计价中心确认成功但 HIS 是否未落账。
- HIS 特殊项目收费是否缺少计价中心追溯记录。
- 退费、作废、撤销是否完成冲正。
- 限额占用是否长期停留在 `PENDING`。
- 折价规则是否应折未折或不应折却折。

对账结果应生成：

- 对账批次。
- 异常明细。
- 财务汇总报表。
- 待处理异常清单。

## 6.5 应急回滚

必须支持：

- 单规则回滚。
- 单项目关闭规则。
- 单渠道关闭调用。
- 切回旧逻辑。

但对于已经启用特殊规则的项目，不建议让外部渠道自行按普通单价收费。

## 7. 需要更新到既有方案的结论

建议将以下内容补入既有设计：

1. 新增限额占用和限额锁设计。
2. 确认计价拆成 `confirm`、`commit`、`cancel`。
3. 新增规则审核流程。
4. 新增规则测试用例和发布前模拟验证。
5. 明确 `NULL` 表示不校验，`0` 不等于不校验。
6. 明确统一取整策略。
7. 明确特殊项目服务异常时不允许渠道自行收费。
8. 明确所有请求都记录日志，只有确认成功进入正式折价结果。

## 8. 最重要的落地优先级

如果时间紧，优先级如下：

1. 幂等。
2. 限额锁和占用。
3. 确认、提交、取消三段式。
4. 折价追溯。
5. 规则版本和审核。
6. 取整策略。
7. 发布前测试。
8. 灰度和回滚。

其中前 4 个是收费稳定性的底线。

## 9. 最终建议

目前方案已经能解决“多端重复改代码”的问题，但要达到“稳定、不出钱账问题”的要求，还必须补上并发、占额、提交一致性、审核、取整、异常兜底这些控制点。

收费系统的稳定性不只来自代码正确，还来自边界正确：

- 试算不能占额。
- 确认必须幂等。
- 落账失败必须释放。
- 退费必须冲正。
- 规则发布必须审核。
