# 设计缺陷与补充方案

## 1. 文档目的

本文基于当前方案文档（01-07）的审查，识别出 25 个设计缺陷，并给出具体补充方案。缺陷按严重程度分为：

- **P0 — 必须在编码前解决**，否则会导致数据错误或并发事故
- **P1 — 应在第一阶段解决**，否则会导致业务流程断裂
- **P2 — 建议在上线前解决**，否则会影响运维和扩展

## 一、数据模型层面

### 缺陷 1（P0）：PR_RULE_DETAIL 与条件/动作表模型未统一

**问题描述：**

02 方案文档第 7.2 节设计了 `PR_RULE_DETAIL` 表，承载计价类型、计价部位、计价单位、基础计价量、换算数量、公式类型等字段。但 04 表设计草案改用 `PR_RULE_CONDITION` + `PR_RULE_ACTION` 两张表来承载这些信息。

两套模型并存，开发者无法确定：折价页签上的字段（计价类型、计价单位、换算数量）到底存到哪里。

**补充方案：**

统一为 **PR_RULE_CONDITION + PR_RULE_ACTION** 模型，废弃 PR_RULE_DETAIL。原因：

1. 条件-动作模型扩展性更强，未来新增规则类型不需要改表结构
2. PR_RULE_DETAIL 本质是条件-动作模型的一个子集特例

但需要做以下补充：

```
PR_RULE_CONDITION 补充以下预定义 CONDITION_TYPE：
  - PRICING_TYPE          -- 计价类型匹配
  - PRICING_UNIT          -- 计价单位匹配
  - BODY_PART_MATCH       -- 计价部位匹配

PR_RULE_ACTION 补充以下预定义 ACTION_TYPE：
  - CONVERT_QTY           -- 双单位换算
  - FORMULA_CALC          -- 公式计算
  - APPLY_BASE_QTY        -- 基础计价量处理
```

同时在 PR_RULE_ACTION 的 PARAMS_JSON 中约定以下标准参数键：

| PARAMS_JSON 键 | 说明 | 示例 |
|---|---|---|
| `pricingTypeCode` | 计价类型编码 | AREA |
| `pricingUnitCode` | 计价单位编码 | CM2 |
| `convertUnitCode` | 换算单位编码 | UNIT |
| `convertQty` | 换算数量 | 1 |
| `convertBaseQty` | 换算基数（多少计价单位=1个换算单位） | 9 |
| `formulaCode` | 公式编码 | INCREMENT_50_PERCENT |
| `formulaParams` | 公式参数 | {"rate": 0.5} |

这样折价页签的字段可以通过标准 PARAMS_JSON 键映射到规则动作中，不需要单独建表。

### 缺陷 2（P0）：LIMIT_KEY 的生成规则未定义

**问题描述：**

PR_LIMIT_LOCK 和 PR_LIMIT_OCCUPY 都依赖 `LIMIT_KEY` 作为锁维度键，但文档只举了一个例子 `DAY:P001:CT001:20260507`。不同限制类型的键格式是什么？谁负责生成？格式不统一会导致锁失效或锁粒度错误。

**补充方案：**

定义完整的 LIMIT_KEY 生成规则：

| 限制类型 | LIMIT_KEY 格式 | 锁粒度 | 说明 |
|---|---|---|---|
| DAY_QTY | `DQ:{patientId}:{itemCode}:{yyyyMMdd}` | 患者+项目+日期 | 单日数量上限 |
| DAY_AMOUNT | `DA:{patientId}:{itemCode}:{yyyyMMdd}` | 患者+项目+日期 | 单日金额上限 |
| ONCE_QTY | `OQ:{chargeNo}:{itemCode}` | 收费单+项目 | 单次数量上限 |
| TIME_WINDOW | `TW:{patientId}:{itemCode}:{windowStartyyyyMMddHH}` | 患者+项目+窗口起始小时 | 2小时窗口 |
| SAME_OPERATION | `SO:{operationNo}:{itemCode}` | 手术号+项目 | 同手术封顶 |
| SAME_PREGNANCY | `SP:{pregnancyNo}:{groupCode}` | 孕次号+项目组 | 同胎次封顶 |
| SAME_GROUP | `SG:{patientId}:{groupCode}:{yyyyMMdd}` | 患者+组+日期 | 同组互斥 |

**规则：**

1. LIMIT_KEY 由统一计价引擎的 Domain 层生成，不由渠道传入
2. 生成逻辑封装在 `LimitKeyGenerator` 类中，每种 LIMIT_TYPE 对应一个生成方法
3. 所有键值统一转大写，避免大小写不一致导致锁重复
4. TIME_WINDOW 的窗口起始时间计算方式见缺陷 4

### 缺陷 3（P1）：PR_RULE_HEADER 与条件/动作表的版本一致性

**问题描述：**

PR_RULE_HEADER.CURRENT_VERSION 指向当前版本号，PR_RULE_CONDITION 和 PR_RULE_ACTION 都带 VERSION_NO 字段。版本升级时需要同时更新多张表，没有说明如何保证跨表版本一致性。

**补充方案：**

1. 规则版本升级时，**不修改已有版本的条件和动作记录**，而是新增一组带新版本号的记录
2. PR_RULE_HEADER.CURRENT_VERSION 在发布时原子更新
3. 整个版本发布操作封装在一个数据库事务中：

```
发布流程（同一事务）：
  1. 读取 PR_RULE_HEADER.CURRENT_VERSION
  2. 新版本号 = CURRENT_VERSION + 1
  3. 复制当前版本的所有 PR_RULE_CONDITION 记录，VERSION_NO 改为新版本号
  4. 复制当前版本的所有 PR_RULE_ACTION 记录，VERSION_NO 改为新版本号
  5. 如果是修改后发布，用草稿中的条件/动作替换复制的记录
  6. 更新 PR_RULE_HEADER.CURRENT_VERSION = 新版本号
  7. 插入 PR_RULE_VERSION 记录（含快照）
  8. 插入 PR_RULE_PUBLISH 记录
  9. 插入 PR_RULE_CHANGE_LOG 记录
```

**关键约束：** PR_RULE_CONDITION 和 PR_RULE_ACTION 的 (RULE_ID, VERSION_NO, CONDITION_ID/ACTION_ID) 组合必须唯一，避免版本复制时产生重复。

### 缺陷 4（P0）：2小时窗口的起止时间计算未说明

**问题描述：**

"2小时内收费上限"的"2小时"是从什么时间点开始的？是固定自然时段还是滑动窗口？这直接影响 LIMIT_KEY 构造和累计查询逻辑。

**补充方案：**

采用 **滑动窗口** 模式，定义如下：

1. 窗口起点 = 当前收费时间往前推 TIME_WINDOW_MINUTES 分钟
2. 累计范围 = [当前时间 - TIME_WINDOW_MINUTES, 当前时间]
3. TIME_WINDOW_MINUTES 从 PR_RULE_ACTION 的 PARAMS_JSON 中读取，默认 120 分钟

**LIMIT_KEY 生成规则：**

滑动窗口不能用固定键锁行，需要改为：

```
锁定维度：patientId + itemCode + 窗口起始小时
LIMIT_KEY = TW:{patientId}:{itemCode}:{窗口起始小时yyyyMMddHH}
```

窗口起始小时 = floor(当前时间 到小时)。这样同一个2小时窗口内（如 10:15 和 10:45）会映射到同一个锁键。

**累计查询逻辑：**

```sql
-- 查询窗口内已确认和待确认的累计数量
SELECT NVL(SUM(OCCUPY_QTY), 0)
FROM PR_LIMIT_OCCUPY
WHERE LIMIT_KEY LIKE 'TW:{patientId}:{itemCode}:%'
  AND STATUS IN ('CONFIRMED', 'PENDING')
  AND OCCUPIED_AT >= :windowStart  -- 当前时间 - 120分钟
  AND OCCUPIED_AT <= :currentTime
```

**注意：** 由于同一患者同一项目在相邻小时可能有不同锁键，需要同时锁定当前小时和前一个小时的锁行：

```
1. 构造当前小时锁键：TW:{patientId}:{itemCode}:{当前小时}
2. 构造前一小时锁键：TW:{patientId}:{itemCode}:{前一小时}
3. 按字典序排序后依次 SELECT FOR UPDATE（防止死锁）
4. 查询窗口内累计
```

### 缺陷 5（P1）：PR_CHARGE_REVERSE_LOG 与 PR_LIMIT_OCCUPY 的联动缺失

**问题描述：**

文档说"退费必须冲正额度"，但 PR_CHARGE_REVERSE_LOG 只记录冲正信息，没有说明冲正后如何精确释放 PR_LIMIT_OCCUPY 中的占用记录。部分退费时释放多少额度？

**补充方案：**

定义冲正联动规则：

**全额退费/作废：**

```
1. 查找原确认请求对应的 PR_LIMIT_OCCUPY 记录（通过 REQUEST_ID 关联）
2. 将 STATUS 从 CONFIRMED 改为 REVERSED
3. 无需修改 OCCUPY_QTY 和 OCCUPY_AMT（整条作废即可）
```

**部分退费：**

```
1. 查找原确认请求对应的 PR_LIMIT_OCCUPY 记录
2. 插入一条新的 PR_LIMIT_OCCUPY 记录：
   - REQUEST_ID = 冲正请求ID
   - LIMIT_TYPE = 与原记录相同
   - LIMIT_KEY = 与原记录相同
   - OCCUPY_QTY = -退费数量（负数）
   - OCCUPY_AMT = -退费金额（负数）
   - STATUS = CONFIRMED（立即确认，因为退费本身就是最终操作）
3. 不修改原占用记录（保留审计痕迹）
```

**额度计算时的处理：**

累计查询时，SUM(OCCUPY_QTY) 会自动将负数的退费占用纳入计算，实现额度释放。

**需补充的字段：**

PR_LIMIT_OCCUPY 增加字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `OCCUPY_TYPE` | VARCHAR2(20) | CHARGE（收费占用）、REVERSE（退费释放） |
| `ORIGINAL_OCCUPY_ID` | NUMBER(18,0) | 关联的原占用记录ID（退费时填写） |

### 缺陷 6（P2）：缺少"收费场景"字典定义

**问题描述：**

接口请求中有 `chargeScene` 字段（OUTPATIENT_CHARGE、SURGERY_CHARGE 等），但 PR_DICT 中没有定义收费场景字典。不同渠道传入的场景值可能不统一。

**补充方案：**

在 PR_DICT 中增加收费场景字典：

```
DICT_TYPE = CHARGE_SCENE

预定义值：
  OUTPATIENT_CHARGE     -- 门诊收费
  INPATIENT_CHARGE      -- 住院收费
  SURGERY_CHARGE        -- 手术批费
  SUPPLEMENT_CHARGE     -- 补缴费
  EMERGENCY_CHARGE      -- 急诊收费
  SELF_MACHINE_CHARGE   -- 自助机收费
  WECHAT_CHARGE         -- 微信公众号收费
```

**规则：**

1. 各渠道传入的 chargeScene 必须在字典中存在，否则返回 INVALID_REQUEST
2. 规则匹配时按 chargeScene 进行条件匹配
3. 字典支持扩展，新增场景只需加字典记录，不改代码

### 缺陷 7（P0）：规则匹配的"唯一命中"还是"多条叠加"未明确

**问题描述：**

一个项目可能同时配置了多条规则（如一条金额上限规则 + 一条2小时窗口规则 + 一条公式规则）。命中多条规则时，是只取优先级最高的那条执行，还是所有命中规则依次执行？

**补充方案：**

定义 **多规则叠加执行** 模型：

**匹配阶段：**

```
1. 按项目编码查询所有 IS_ENABLED='Y' 且 STATUS='PUBLISHED' 的规则
2. 按 EFFECTIVE_FROM 和 EFFECTIVE_TO 过滤生效规则
3. 对每条规则，逐一评估其所有条件（PR_RULE_CONDITION）
4. 所有条件都满足的规则 = 命中规则集合
5. 按 PRIORITY 排序（数字越小优先级越高）
```

**执行阶段：**

```
1. 按 PRIORITY 顺序遍历命中规则
2. 每条规则的 PR_RULE_ACTION 按 SORT_NO 顺序执行
3. 所有规则的动作都执行完毕后，汇总最终结果
```

**动作执行顺序的全局约束：**

当多条规则的动作混合执行时，需要保证全局执行顺序：

```
第一步：CONVERT_QTY（所有规则的换算动作）
第二步：FORMULA_CALC（所有规则的公式动作）
第三步：APPLY_MIN_AMOUNT（金额下限）
第四步：APPLY_MAX_AMOUNT（金额上限）
第五步：APPLY_DAY_LIMIT_QTY（日数量限制）
第六步：APPLY_TIME_WINDOW_LIMIT（时间窗限制）
第七步：APPLY_ONCE_LIMIT_QTY（单次数量限制）
第八步：SAME_GROUP_MUTEX（同组互斥）
第九步：ADD_CHILD_ITEM（子项加收）
第十步：DISCOUNT_EXCEED_TO_ZERO（超出折为0）
```

**实现方式：**

在 Domain 层的 `PricingEngine` 中，先收集所有命中规则的全部动作，按 ACTION_TYPE 分组，再按上述全局顺序执行。每组内按规则 PRIORITY + 动作 SORT_NO 排序。

### 缺陷 8（P1）：公式执行器的参数传递机制未设计

**问题描述：**

PR_FORMULA_DEF 有 PARAM_SCHEMA_JSON 定义参数结构，但公式运行时的实际参数从哪来？是 PR_RULE_ACTION 的 PARAMS_JSON？还是请求的 extraParams？

**补充方案：**

定义三层参数合并机制：

```
公式执行时的参数 = 规则配置参数（优先） ∪ 请求传入参数 ∪ 系统默认参数

1. 规则配置参数：来自 PR_RULE_ACTION.PARAMS_JSON 中的 formulaParams
   例如：{"fullQty": 1, "rate": 0.5}

2. 请求传入参数：来自 PricingRequest.extraParams
   例如：{"area": 18, "areaUnit": "CM2", "isChild": true}

3. 系统默认参数：引擎自动注入
   例如：{"unitPrice": 200, "convertedQty": 2, "patientAge": 7}
```

**参数传递流程：**

```
1. 引擎构造 PricingContext 对象
2. PricingContext.FormulaParams = 合并后的参数字典
3. 公式执行器从 PricingContext.FormulaParams 中读取所需参数
4. 公式执行器只读取自己需要的键，忽略未知键
```

**PR_FORMULA_DEF 的 PARAM_SCHEMA_JSON 需补充：**

```json
{
  "required": ["unitPrice", "convertedQty"],
  "optional": ["rate", "fullQty", "baseAmount", "area", "isChild"],
  "defaults": {
    "fullQty": 1,
    "rate": 1.0,
    "baseAmount": 0
  }
}
```

公式执行器在运行前校验 required 参数是否都存在，缺少时返回 CALCULATION_FAILED 错误。

### 缺陷 9（P2）：金额下限的全局限制含义未澄清

**问题描述：**

"单日收费下限金额"在业务上意味着什么？如果患者当天只做了1次收费，金额低于下限，是补到下限还是按原价？下限是针对单次还是当日累计？

**补充方案：**

需要分两种情况讨论，建议向业务确认后选择：

**方案 A：单次下限（推荐）**

下限针对单次收费。含义：单次计算金额低于下限时，取下限金额。

适用场景：某些项目有最低收费标准，如"不足100元按100元收"。

```
finalAmount = max(calculatedAmount, minAmount)
```

**方案 B：单日累计下限**

下限针对当日累计收费。含义：当日累计金额低于下限时，在最后一次收费时补差。

适用场景：少见，但可能存在"当日至少收XX元"的规则。

```
当日累计 = SUM(已确认金额) + 本次计算金额
if 当日累计 < dayMinAmount:
    本次补差 = dayMinAmount - SUM(已确认金额)
    finalAmount = max(calculatedAmount, 补差)
```

**建议：** 默认采用方案 A（单次下限），在 PR_RULE_ACTION 的 PARAMS_JSON 中增加 `limitScope` 字段区分：

| limitScope | 说明 |
|---|---|
| SINGLE | 单次下限（默认） |
| DAY_ACCUMULATED | 单日累计下限 |

### 缺陷 10（P1）：缺少"部分退费"场景的完整计价逻辑

**问题描述：**

确认计价时占用的是完整额度，部分退费只退了一部分。退费后额度怎么释放？重新收费时额度怎么算？

**补充方案：**

定义部分退费的完整流程：

**场景：单日上限3次，已确认3次，退费1次后是否还能再收1次？**

```
原始状态：
  PR_LIMIT_OCCUPY 中有3条 CONFIRMED 记录
  OCCUPY_QTY 分别为 1, 1, 1
  累计 = 3，已达上限

退费1次后：
  PR_LIMIT_OCCUPY 新增1条记录
  OCCUPY_QTY = -1, OCCUPY_TYPE = REVERSE
  累计 = 3 + (-1) = 2
  剩余额度 = 1

再收费1次：
  累计 = 2 + 1 = 3，未超上限，允许收费
```

**部分退费（退数量不退整笔）：**

```
原始状态：
  某次确认：OCCUPY_QTY = 3（收了3个部位）

部分退费（退1个部位）：
  新增记录：OCCUPY_QTY = -1, OCCUPY_TYPE = REVERSE
  累计净占用 = 3 + (-1) = 2
```

**金额释放：**

```
PR_LIMIT_OCCUPY 中 OCCUPY_AMT 同样支持负数
退费1个部位：OCCUPY_AMT = -300（假设单价300）
累计金额 = SUM(OCCUPY_AMT) 自动扣除
```

**关键约束：**

1. 退费数量不能超过原确认数量（引擎校验）
2. 退费的 LIMIT_KEY 必须与原确认一致
3. 退费记录的 STATUS 直接为 CONFIRMED（退费无需三阶段）

### 缺陷 11（P1）：确认接口返回结果的"最终性"问题

**问题描述：**

confirm 接口返回了 finalAmount，但 HIS 落账失败后调 cancel 释放额度，另一个渠道又立即确认了同一项目的收费——额度已变，之前返回的 finalAmount 可能已不准确。confirm 的结果是否需要加有效期？

**补充方案：**

**方案 A：confirm 结果加有效期（推荐）**

在响应中增加 `expireAt` 字段：

```json
{
  "traceId": "TR202605070001",
  "finalAmount": 900,
  "expireAt": "2026-05-07T11:00:00",
  "expireSeconds": 1800
}
```

有效期规则：

1. 默认 30 分钟（可配置）
2. 超过有效期后，后台任务自动将占用标记为 EXPIRED 并释放额度
3. HIS 必须在有效期内完成落账并调 commit
4. 超过有效期后调 commit 返回 EXPIRED 错误，HIS 需重新 confirm

**方案 B：confirm 结果不保证最终性**

接受 confirm 结果仅是"当时那一刻的计算结果"，HIS 以 commit 的成功/失败为准。但需要在文档中明确告知调用方。

**建议采用方案 A**，并在 PR_LIMIT_OCCUPY 表中已有 EXPIRE_AT 字段的基础上，增加后台清理任务：

```
定时任务（每5分钟）：
  UPDATE PR_LIMIT_OCCUPY
  SET STATUS = 'EXPIRED'
  WHERE STATUS = 'PENDING'
    AND EXPIRE_AT < SYSDATE
```

### 缺陷 12（P2）：追溯查询接口缺少分页和排序

**问题描述：**

`POST /api/pricing/trace/query` 的响应设计中没有分页参数。一个患者一年的收费记录可能有几千条，不分页会导致性能问题和超时。

**补充方案：**

请求模型增加分页和排序字段：

```json
{
  "patientId": "P001",
  "chargeNo": "C000001",
  "itemCode": "CT001",
  "dateFrom": "2026-05-01",
  "dateTo": "2026-05-07",
  "pageIndex": 1,
```

### 缺陷 14（P1）：接口缺少超时和降级策略

**问题描述：**

**补充方案：**

**超时阈值：**

| 接口 | 超时阈值 | 说明 |
|---|---|---|
| simulate | 3秒 | 试算允许宽松一些 |
| confirm | 5秒 | 确认需要更可靠 |
| special-flag | 1秒 | 轻量查询，必须快 |
| batch-simulate | 10秒 | 按项目数量动态调整 |

**超时响应：**

```json
{
  "success": false,
  "errorCode": "SERVICE_TIMEOUT",
  "errorMessage": "计价服务响应超时，请稍后重试"
}
```

**降级策略：**

```
special-flag 接口：
  - 超时或异常时返回 {"special": true}
  - 即：宁可多调一次计价服务，也不能漏掉特殊项目
  - 渠道收到 special=true 但计价服务异常时，提示"请稍后重试"或"请到人工窗口"

simulate 接口：
  - 超时后渠道不展示价格，提示"价格计算中，请稍候"
  - 不允许按默认单价展示

confirm 接口：
  - 超时后不允许收费
  - 提示"计价服务暂时不可用，请稍后重试"
```

**熔断机制：**

建议在渠道侧实现简单熔断：

```
1. 连续5次调用失败或超时，触发熔断
2. 熔断期间（30秒），直接返回 SERVICE_UNAVAILABLE
3. 熔断期间不调用计价服务，减少无效请求
4. 30秒后进入半开状态，允许1次试探请求
5. 试探成功则恢复，失败则继续熔断
```

### 缺陷 15（P1）：缺少规则变更的实时通知机制

**问题描述：**

规则发布后要立即失效缓存，但如果各渠道本地缓存了 special-flag 结果，如何感知规则变更？

**补充方案：**

**方案 A：special-flag 不缓存（推荐初期使用）**

special-flag 接口每次实时查询数据库。理由：

1. 这是一个轻量查询（只查 IS_ENABLED 和 STATUS）
2. 规则变更频率极低（每天最多几次）
3. 查询走索引 ITEM_CODE + IS_ENABLED + STATUS，性能足够

**方案 B：缓存 + 版本号比对（推荐长期使用）**

1. 规则发布时，全局版本号（PR_RULE_HEADER 表的 UPDATED_AT 最大值）自动更新
2. 渠道请求时在 Header 中带上上次获取的版本时间戳
3. 服务端比对版本时间戳，如果规则有变更，返回新的 special-flag 结果
4. 如果无变更，返回 304 Not Modified

```
请求：
GET /api/pricing/items/{itemCode}/special-flag
If-Modified-Since: 2026-05-07T10:00:00

响应（规则未变）：
HTTP 304 Not Modified

响应（规则已变）：
HTTP 200 OK
{
  "special": true,
  "lastModified": "2026-05-07T11:30:00"
}
```

**方案 C：规则发布时主动推送**

1. 规则发布后，计价服务通过消息队列（如 RabbitMQ）或 Webhook 通知各渠道
2. 各渠道收到通知后清除本地缓存
3. 缺点：增加架构复杂度，且需要各渠道实现消费者

**建议：** 初期用方案 A，上线稳定后优化为方案 B。

### 缺陷 16（P0）：SELECT FOR UPDATE 在高并发下的性能隐患

**问题描述：**

PR_LIMIT_LOCK 表用 SELECT FOR UPDATE 锁行，全院所有渠道的同项目收费都锁同一行。门诊早高峰时可能成为瓶颈。

**补充方案：**

**短期优化：锁粒度细化**

当前锁粒度是 `患者 + 项目 + 日期`（DAY_QTY）或 `患者 + 项目 + 窗口小时`（TIME_WINDOW）。

在大多数场景下，这个粒度已经足够细：

1. 不同患者之间不互锁
2. 同一患者同一项目同一时刻通常只有一个渠道在操作
3. 真正的并发场景是：HIS 和自助机同时给同一患者同一项目收费

**中期优化：乐观锁替代悲观锁**

```
方案：
1. 不使用 SELECT FOR UPDATE
2. 先读取当前累计值（无锁）
3. 计算新累计值
4. 使用 UPDATE ... WHERE 条件更新：
   UPDATE PR_LIMIT_LOCK
   SET UPDATED_AT = SYSDATE
   WHERE LOCK_KEY = :lockKey
     AND UPDATED_AT = :readTime
5. 如果 UPDATE 影响行数 = 0，说明被其他事务修改过，重试
6. 重试上限 3 次
```

**性能对比：**

| 方案 | 优点 | 缺点 |
|---|---|---|
| SELECT FOR UPDATE | 强一致，不需重试 | 高并发下锁等待 |
| 乐观锁 | 无锁等待 | 冲突时需重试 |

**建议：** 初期用 SELECT FOR UPDATE（简单可靠），监控锁等待时间，如果 P99 超过 100ms 则切换到乐观锁。

### 缺陷 17（P1）：confirm 和 commit 之间的"悬空占用"缺少具体清理策略

**问题描述：**

文档提到"后台定时扫描 CONFIRM_PENDING"，但没有给出具体参数。

**补充方案：**

**超时时间设定：**

| 场景 | 超时时间 | 说明 |
|---|---|---|
| 门诊收费 | 15 分钟 | 门诊操作快，15分钟足够 |
| 住院收费 | 30 分钟 | 住院可能需要更多审批步骤 |
| 手术批费 | 60 分钟 | 手术场景复杂，时间更长 |
| 自助机 | 10 分钟 | 自助机流程简单 |
| 微信公众号 | 15 分钟 | 用户可能犹豫，但不会太久 |

超时时间从 PR_LIMIT_OCCUPY.EXPIRE_AT 读取。EXPIRE_AT 在 confirm 时由引擎根据 sourceSystem 设置。

**清理任务实现：**

```
定时任务（每5分钟执行一次）：

1. 查询超时记录：
   SELECT OCCUPY_ID, REQUEST_ID, TRACE_ID, PATIENT_ID, ITEM_CODE
   FROM PR_LIMIT_OCCUPY
   WHERE STATUS = 'PENDING'
     AND EXPIRE_AT < SYSDATE

2. 对每条超时记录：
   a. 更新 STATUS = 'EXPIRED'
   b. 关联更新 PR_CHARGE_REQUEST_LOG 的超时标记
   c. 写入清理日志

3. 生成超时统计报表（供运维查看）
```

**误杀防护：**

1. 清理任务执行前，先检查 PR_CHARGE_REQUEST_LOG 中该请求是否已收到 commit
2. 如果 commit 已到达但状态更新延迟，跳过清理
3. 清理日志必须记录，便于排查"为什么额度被释放了"

### 缺陷 18（P2）：幂等校验缺少"参数不一致"时的具体处理

**问题描述：**

文档说"请求号重复但参数不一致时返回错误"，但没有说明具体行为。

**补充方案：**

**幂等校验逻辑：**

```
1. 收到请求，检查 sourceSystem + requestNo 是否已存在
2. 如果不存在：正常处理，写入请求日志
3. 如果存在：
   a. 比对请求参数（核心字段：itemCode, inputQty, patientId, unitPrice）
   b. 参数一致：直接返回上次的结果（从 PR_CHARGE_REQUEST_LOG.RESPONSE_JSON 读取）
   c. 参数不一致：返回 IDEMPOTENT_CONFLICT 错误
```

**IDEMPOTENT_CONFLICT 响应：**

```json
{
  "success": false,
  "errorCode": "IDEMPOTENT_CONFLICT",
  "errorMessage": "请求号 REQ001 已被使用，但本次请求参数与上次不一致。请使用新的请求号重试。",
  "originalRequestAt": "2026-05-07T10:30:00",
  "originalTraceId": "TR202605070001"
}
```

**HIS 侧的补偿逻辑：**

```
1. HIS 发送 confirm 请求
2. 收到 IDEMPOTENT_CONFLICT
3. HIS 生成新的 requestNo（如追加时间戳后缀）
4. 用新 requestNo 重新请求
```

**约束：**

1. 不允许覆盖已有请求的结果（防止误操作）
2. IDEMPOTENT_CONFLICT 只在 confirm 和 reverse 接口校验
3. simulate 接口不校验幂等（试算可以重复）

### 缺陷 19（P1）："同项目不同部位不同规则"的数据模型支撑不足

**问题描述：**

需求明确提到"头面部4平方厘米=1个，躯干部144平方厘米=1个"，但 PR_RULE_CONDITION 的 BODY_PART_MATCH 条件如何与换算参数关联？一个规则的条件-动作对如何按部位分流？

**补充方案：**

**模型设计：一个项目多条规则，每条规则带部位条件**

```
规则1：
  条件：ITEM_CODE = 'SKIN001' AND BODY_PART = 'HEAD'
  动作：CONVERT_QTY, convertBaseQty = 4

规则2：
  条件：ITEM_CODE = 'SKIN001' AND BODY_PART = 'TRUNK'
  动作：CONVERT_QTY, convertBaseQty = 144

规则3（通用兜底）：
  条件：ITEM_CODE = 'SKIN001'（无部位条件）
  动作：CONVERT_QTY, convertBaseQty = 9（默认）
```

**匹配逻辑：**

```
1. 查询项目的所有规则
2. 按 PRIORITY 排序
3. 逐一评估条件
4. 如果部位条件匹配，命中该规则
5. 如果没有部位匹配的规则，命中兜底规则（无部位条件的）
6. 只有1条规则命中（不叠加同类型的换算动作）
```

**关键约束：**

- 同一 ACTION_TYPE 只执行一次（不叠加多个 CONVERT_QTY）
- 当多条规则都有 CONVERT_QTY 但部位不同时，只执行条件匹配的那条
- 在 PR_RULE_ACTION 中增加 `EXCLUSIVE_GROUP` 字段，同组动作互斥

PR_RULE_ACTION 补充字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `EXCLUSIVE_GROUP` | VARCHAR2(50) | 互斥组编码。同组内只执行优先级最高的动作 |

示例：

```
规则1 的动作：ACTION_TYPE=CONVERT_QTY, EXCLUSIVE_GROUP=CONVERT
规则2 的动作：ACTION_TYPE=CONVERT_QTY, EXCLUSIVE_GROUP=CONVERT
规则3 的动作：ACTION_TYPE=FORMULA_CALC, EXCLUSIVE_GROUP=FORMULA
```

执行时，CONVERT 组只执行优先级最高的那条，FORMULA 组也只执行优先级最高的那条。

### 缺陷 20（P1）：缺少"加收子项目"的联动设计

**问题描述：**

文档提到"儿童加收30%"，但子项目的生成逻辑在哪里？是引擎自动生成还是返回给 HIS？金额依赖主项目结果，主项目还没最终确认时子项目怎么算？

**补充方案：**

**子项目生成方式：引擎生成，返回给 HIS**

```
计价响应中增加字段：
{
  "success": true,
  "finalAmount": 900,
  "childItems": [
    {
      "itemCode": "CHILD_001",
      "itemName": "儿童加收",
      "baseItemCode": "CT001",
      "calculationType": "MAIN_ITEM_PERCENT",
      "rate": 0.3,
      "amount": 270,
      "reasonDesc": "按主项目金额900元的30%加收"
    }
  ]
}
```

**生成逻辑：**

```
1. 主项目计价完成后，引擎检查 PR_RULE_ACTION 中的 ADD_CHILD_ITEM 动作
2. 读取 PARAMS_JSON 中的子项目配置：
   {
     "childItemCode": "CHILD_001",
     "childItemName": "儿童加收",
     "calculationType": "MAIN_ITEM_PERCENT",
     "rate": 0.3,
     "condition": "isChild == true"
   }
3. 评估条件（如 extraParams.isChild == true）
4. 条件满足则计算子项目金额 = 主项目 finalAmount * rate
5. 将子项目结果加入响应的 childItems 数组
```

**HIS 侧处理：**

```
1. HIS 收到计价响应
2. 检查 childItems 是否非空
3. 非空则自动添加子项目收费明细
4. 子项目金额由引擎计算，HIS 不自行计算
```

**追溯记录：**

子项目也在 PR_CHARGE_DISCOUNT_DETAIL 中记录，DISCOUNT_TYPE = 'CHILD_ITEM'，关联主项目的 REQUEST_ID。

### 缺陷 21（P2）：历史规则迁移缺少"映射失败"的降级方案

**问题描述：**

**补充方案：**

**迁移分类：**

```
A类 — 可直接映射（约50条）：

  - 固定比例递增（50%、70%）

  → 直接写 SQL 脚本导入 PR_RULE_HEADER + CONDITION + ACTION

B类 — 需新建执行器（约15条）：

C类 — 无法映射（约9条）：

  → 降级处理方案见下
```

```
  - 运行时动态编译执行
  - 风险：安全性和性能不可控

方案3：人工处理
  - C类规则暂不迁移
  - 在计价引擎中返回"需人工审核"标记
  - 收费员手工处理
```

**建议采用方案1**，并建立迁移跟踪表：

| MIGRATION_TYPE | A/B/C |

### 缺陷 23（P2）：每日对账缺少"HIS未调用计价服务"的检测

**问题描述：**

**补充方案：**

**检测逻辑：**

```
每日对账增加一项核对：

1. 从 HIS 收费明细中筛选：
   - 项目编码在 PR_RULE_HEADER 中有已发布规则
   - 但 PR_CHARGE_REQUEST_LOG 中没有对应记录

SELECT h.CHARGE_NO, h.ITEM_CODE, h.ITEM_NAME, h.AMOUNT
FROM HIS_CHARGE_DETAIL h
WHERE h.CHARGE_DATE = :reconDate
  AND h.ITEM_CODE IN (
    SELECT ITEM_CODE FROM PR_RULE_HEADER
    WHERE STATUS = 'PUBLISHED' AND IS_ENABLED = 'Y'
  )
  AND NOT EXISTS (
    SELECT 1 FROM PR_CHARGE_REQUEST_LOG r
    WHERE r.CHARGE_NO = h.CHARGE_NO
      AND r.ITEM_CODE = h.ITEM_CODE
      AND r.CALL_TYPE = 'CONFIRM'
      AND r.IS_SUCCESS = 'Y'
  )
```

**异常分级：**

| 情况 | 级别 | 说明 |
|---|---|---|
| HIS收费有计价记录 | 正常 | - |
| HIS收费无计价记录，项目有规则 | L1 | 可能漏调，差额 = 规则折价金额 |
| HIS收费无计价记录，项目无规则 | 正常 | 普通项目，不需计价 |

**补偿处理：**

发现 L1 异常后：

1. 用 HIS 的收费参数重新调用 simulate 试算
2. 对比试算结果和 HIS 实际金额
3. 如果一致：可能是渠道走了旧逻辑但结果碰巧正确，标记为 L3
4. 如果不一致：标记为 L1，生成差额清单给财务处理

### 缺陷 24（P2）：规则配置错误的"预发布验证"流程不完整

**问题描述：**

虽然设计了 PR_RULE_TEST_CASE 和 PR_RULE_TEST_RUN，但没有说明：测试用例谁来写？覆盖率要求？不通过时是阻断发布还是警告？

**补充方案：**

**测试用例来源：**

| 来源 | 说明 | 优先级 |
|---|---|---|
| 历史案例 | 从 01 文档的典型案例提取 | 必须 |
| 规则迁移 | 从 xlsx 中的规则描述提取输入输出 | 必须 |
| 边界值 | 系统自动生成边界测试（0、NULL、超大值） | 建议 |
| 业务补充 | 物价管理员补充特殊场景 | 建议 |

**覆盖率要求：**

```
发布前必须满足：
  1. 至少有1条测试用例覆盖规则的正向场景
  2. 至少有1条测试用例覆盖边界场景（如恰好等于上限）
  3. 所有启用的测试用例全部通过

不满足时：
  - 阻断发布
  - 提示"请补充测试用例或修复失败用例"
```

**自动测试用例生成：**

引擎在规则保存时，自动生成边界测试用例模板：

```
对于金额上限规则，自动生成：
  CASE 1: 金额 = 上限 - 1（应不触发折价）
  CASE 2: 金额 = 上限（应不触发折价）
  CASE 3: 金额 = 上限 + 1（应触发折价，折1元）

对于数量上限规则，自动生成：
  CASE 1: 累计数量 = 上限 - 1，本次1个（应允许）
  CASE 2: 累计数量 = 上限，本次1个（应折价为0）
```

自动生成的用例标记为 AUTO_GENERATED，期望值需要人工填写或由引擎基于旧逻辑推算。

### 缺陷 25（P1）：缺少"同一手术封顶"的标识来源设计

**问题描述：**

文档多次提到"同一手术封顶"，但没有说明手术标识从哪来。PR_RULE_CONDITION 有 SAME_OPERATION 类型，但 LEFT_KEY 取什么值？是手术申请号、手术安排号还是医嘱号？

**补充方案：**

**手术标识来源：**

| 来源 | 字段 | 说明 |
|---|---|---|
| 请求传入 | extraParams.operationNo | 渠道必须传入手术标识 |
| 规则配置 | PR_RULE_CONDITION.RIGHT_VALUE | 定义标识的格式要求 |

**约束：**

1. 如果规则条件中有 SAME_OPERATION，请求必须携带 operationNo
2. operationNo 为空时，引擎返回 RULE_MATCH_FAILED 错误
3. operationNo 的格式不校验（由 HIS 保证）

**LIMIT_KEY 生成：**

```
SAME_OPERATION 类型的 LIMIT_KEY：
  SO:{operationNo}:{itemCode}

示例：
  SO:OP20260507001:SKIN001
```

**同组封顶的实现：**

```
1. 规则条件：SAME_OPERATION + GROUP_MATCH
2. LIMIT_KEY = SO:{operationNo}:{groupCode}
3. 同一手术下同组项目共享一个限额
4. 超出部分折价为0
```

**PR_RULE_CONDITION 补充：**

对于 SAME_OPERATION 条件类型，LEFT_KEY = 'OPERATION_NO'，RIGHT_VALUE 为空（表示只要请求中有 operationNo 即匹配）。

如果需要匹配特定手术类型：

```
LEFT_KEY = 'OPERATION_TYPE'
RIGHT_VALUE = 'MAJOR_SURGERY'
OPERATOR_TYPE = 'EQ'
```
