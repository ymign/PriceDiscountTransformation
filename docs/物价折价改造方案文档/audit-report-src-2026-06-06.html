📝 总体评估

📋 总体评估

项目概况：这是一个 .NET 6 + ASP.NET Core + SqlSugar + Oracle 11g 的医院物价折价规则中心。src 内已经具备 API、Application、Domain、Infrastructure 分层，规则匹配、动作执行、发布门禁、幂等、限额占用、过期清理、追溯日志、权威单价校验等核心部件都有实现。

主要风险：最大问题不是“完全不能用”，而是上线边界不够硬：敏感接口缺少代码层认证授权；规则发布提交后再做缓存失效，多实例下可能出现已发布规则与运行期缓存短暂不一致；规则能力仍依赖静态常量和 DI 注册，不能承诺所有未来政策都只靠配置解决。

亮点：资金链路的方向是对的。confirm/commit/cancel/reverse 有独立状态推进，限额采用 SELECT FOR UPDATE，业务时间 BusinessChargeTime 已经进入限额和匹配流程，发布前有审批、测试用例、冲突、参数和能力门禁。`dotnet test src\Pricing.RuleCenter.slnx --no-restore` 当前通过 300 个测试。

优先修复：先补认证授权和发布缓存失效一致性，再把规则能力注册做成一张可测试的能力矩阵，随后拆分计价基类和发布基类，最后补 Oracle 并发、多实例缓存、配置启动校验和 API 错误契约测试。

总评：B / 5.8。工程骨架和业务意识明显存在，但还没到稳定上线级别。若目标是“以后国家物价局规则通过配置解决”，当前只能覆盖已抽象出的条件、动作和表达式公式；新增业务语义、限额维度或动作副作用仍需要代码扩展和回归测试。

3. 规则引擎不是任意未来规则都能纯配置表达

Medium Confirmed
📁 Architecture / Type Safety 📍 Program.cs:105-147, RuleCapabilityCodes.cs:53/137/209, RuleCapabilityGuard.cs:35/65 🎯 条件、动作、执行器能力模型
问题：当前引擎支持“已有条件 + 已有动作 + 表达式公式”的配置化组合，但不支持任意新增政策语义都纯配置落地。新增条件维度、新限额动作、新副作用动作仍需要新增 evaluator/executor、DI 注册和能力码白名单。也就是说，它可以显著减少硬编码，但不能承诺国家物价局以后所有新规则都“一劳永逸只改配置”。
