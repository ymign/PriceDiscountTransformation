## 3. 仍未关闭的问题

### 3.1 原问题 3：规则能力模型仍是“静态白名单 + 手工 DI 注册”

当前代码仍没有形成单一能力源：

- `src/API/Program.cs:152-185` 仍然手工注册全部 `IRuleConditionEvaluator` / `IRuleActionExecutor`
- `src/Application/Application/Rules/Guards/RuleCapabilityGuard.cs:35/52/65/73` 仍依赖 `RuleConditionTypeCodes`、`RuleActionTypeCodes`、`FormulaExecutorCodes` 的静态判断
- `src/Domain/Constants/RuleCapabilityCodes.cs` 仍然维护支持集合

这意味着新增一个规则能力时，仍要同时改：

- 执行器实现
- DI 注册
- 能力常量/白名单
- 发布门禁

结论：原报告“不是任意未来规则都能纯配置表达”的判断仍成立。

建议优先级：`高`

建议补齐：

- 引入 `RuleCapabilityRegistry`
- 启动时从 DI 自动生成运行期能力矩阵
- 发布门禁、字典能力、执行器能力统一使用同一份 registry
- 加契约测试，防止“执行器已注册但发布门禁没放行”或反向漂移

### 3.3 原问题 10：核心类仍然过大，而且比审计时更大

当前主要大文件行数如下：

- `src/Application/Application/Pricing/UseCases/PricingUseCaseBase.cs`：`970` 行
- `src/Application/Application/Rules/Publishing/RulePublishUseCaseBase.cs`：`667` 行
- `src/Application/Application/Engine/RuleMatchService.cs`：`602` 行
- `src/Application/Dto/PricingDto.cs`：`594` 行

这说明之前的结构性拆分还没有真正落地，甚至 `PricingUseCaseBase`、`RulePublishUseCaseBase` 比审计报告里的行数更高。

结论：原报告的可维护性问题未关闭，而且已经有继续膨胀的迹象。

建议优先级：`中高`

建议补齐：

- 把 `PricingUseCaseBase` 按 `simulate / confirm / commit / cancel / reverse / idempotency` 拆成 workflow
- 把 `RulePublishUseCaseBase` 按 `publish / disable / rollback / outbox invalidate` 拆开
- DTO 文件按查询/命令/响应拆分，避免继续堆在 `PricingDto.cs`

## 4. 部分关闭，但还需要继续完善的问题
