Technical Briefing

旧 HIS 不是“最后统一结算一次”，而是界面层先多次预演，再由规则类逐项改写金额与数量。

如果你正在排查“为什么某条项目显示金额变了”“为什么组套主项金额不对”“为什么提交前又被改了一次”，这页可以直接告诉你该从哪个方法和哪条链路开始看。

Overview

先看这一屏，就能建立旧逻辑的整体心智模型

这部分不讲每个方法体细节，只讲“旧系统是怎么组织折价工作的”。先把这层看明白，后面看代码不会乱。

旧逻辑不是统一引擎

不是最后收口到一个单独的 pricing engine，而是界面层和规则类一起完成折价。

显示口径和提交口径都要保证

收费员录完一条就得看到正确金额，真正收费前又必须基于完整列表重新校正。

数量限制是“扣剩余额度”

核心不是拒单，而是把超出部分改成 0 元，或把当前数量截断到可收费的剩余额度。

比例折价是另一条线

不是查历史次数，而是“第 1 个全价，其余按比例”，最后再看是否命中最高限价。

一句话理解旧门诊折价链

如果把旧逻辑压缩成一句话，就是：

先在 ucDisplay 里决定何时重算、用哪批对象重算，再在 Restrictingfee 里按规则真正改数量、改单价、改金额。

所以排查时不要只看某一个方法。你必须同时分清：

  1. 这次重算是在哪个时点触发的。
  2. 当时参与计算的是当前单条、当前页面列表，还是提交前整理后的完整收费集合。
  3. 最后实际执行的是数量限制、比例折价，还是组套拆解后的子项逻辑。

推荐阅读顺序

01
先看 ucDisplay

确认项目是在录入、刷新还是提交前被再次接管。这个决定了“为什么你看到它又被算了一遍”。

02
再看 Restrictingfee

确认命中的到底是数量限制还是比例折价，以及历史次数、本次前序项目是怎么扣掉额度的。

03
最后看组套专题和变量

如果项目属于组套或 DR/CT 特殊组套，就不能只盯主项金额，必须跟进拆子项和回汇过程。

UI Flow

ucDisplay 主链：先决定“何时重算”，再把结果回写到界面或提交对象

ucDisplay 的关键价值不是发明折价算法，而是控制“什么时候触发”和“拿哪批对象去重算”。这正是旧逻辑容易让人误判的地方。

链路 1 / 单条录入时

SetItem(...) 让当前行立刻呈现“已经折价后的样子”

1
先做录入入口的基本准备

校验患者、看诊科室，拉取最新目录价格，确定项目类型，保证当前对象已经具备后续折价需要的基础字段。

2
如果是组套，就递归展开子项

这里不是简单保留主项收费，而是通过递归调用 SetItem 把组套成员逐个挂进来，为后续逐子项处理做准备。

3
当前行即时回算

调用 SetRestrictingfee + ConvertRestrictingfeeCharge，把当前行显示金额、数量立刻修正到旧规则口径。

链路 2 / 界面刷新时

SetChargeInfo() 让整页显示重新对齐同一口径

1
先清空界面，再按当前列表重组

以 alChargeInfo 为准重新落格，避免界面上残留旧对象或旧金额。

2
遍历每条项目决定是否进入限制收费链

若该项目属于限制收费项目，且当前科室不是 7021，就先用 ConvertRestrictingfeeCharge 改金额后再显示。

3
删除旧对象，补回重算后的对象

这一步决定了为什么你在界面上看到的对象，已经不是最初录入时那一版实例，而是被规则逻辑接管后的版本。

4
最后再补显示层属性

例如年龄价、公费显示、自费记账标识、彩超差额口径、行头提示等。这些不一定改变折价结果，但会影响收费员看到的最终画面。

链路 3 / 真正收费前

GetFeeItemList() 用完整收费集合再兜底重算一次

1
GetFeeItemListForCharge() 先收集可提交行

它只负责从表格里挑出当前允许提交收费的对象，本身不做最终折价计算。

2
GetFeeItemList() 做提交前整理

补开单科室、拆组套、处理 DR/CT 只收一次去重，让参与最终结算的对象集合变得完整且可计算。

3
再次执行限制收费逻辑

调用 SetRestrictingfee + ConvertRestrictingfee，基于完整收费集合重新扣一次剩余额度，作为最终收费对象。

为什么旧系统会“算 2 次甚至 3 次”
录入时先保证当前行立刻正确；整页刷新时再保证整个列表同口径；真正提交前还要因为中间可能新增、删除了项目，再基于完整集合做一次兜底。所以这不是重复 bug，而是旧界面逻辑为了保证显示口径和提交口径一致而刻意重复计算。
Rule Flow

Restrictingfee 主链：真正改数量、改金额、扣额度的地方在这里

如果 ucDisplay 决定了“何时算”，那 Restrictingfee 就决定了“怎么算”。下面四块就是旧规则里最关键的四条算法线。

数量限制折价：ConvertRestrictingfee

这条线最像“剩余额度扣减器”。先查历史已收费次数，再扣本次前序项目已经占掉的额度，然后决定当前项目还能保留多少。

历史已收费次数 = getRestrictingfee(...) 或 getRestrictingfeeZT(...)
剩余额度 = LimitNumber - 历史次数 - 本次前序已占数量

if 剩余额度 <= 0:
    当前项目金额 = 0
elif 剩余额度 < 当前数量:
    当前项目数量截断为剩余额度
    当前项目金额 = 单价 × 剩余额度
else:
    当前项目完整保留

比例折价：ConvertDiscountfee

这条线不是看历史次数，而是按“第 1 个全价，其余按折扣率”，最后再判断是否命中最高限价 TOPPRICE。

金额 = 第 1 个全价
     + (其余数量 × 单价 × DISCOUNT_RATE)

如果 TOPPRICE > 0:
    最终金额 = min(上面算出的金额, TOPPRICE)

组套数量限制：ConvertRestrictingfeeCharge

组套不是对主项直接做限次，而是先拆子项、逐子项扣额度，再把还能收费的结果重新汇总回主项金额。

1. 把组套主项拆成明细子项
2. 子项逐个查历史收费次数
3. 再扣本次前序项目、前序组套子项已占额度
4. 把仍可收费的子项金额汇总回主项

住院版：ConvertRestrictingfeeZY / ConvertDiscountfeeZY

门诊版和住院版骨架一致，只是作用对象从门诊收费对象换成住院费用对象。也就是说，旧系统并不是两套完全不同的折价思想，而是同一套路应用到不同对象模型上。

先查历史次数
再扣本次前序项目
再做床旁 / 胎心 / 分组互斥
最后按数量截断或比例折价回写金额
Package Flow

组套专题：主项只是“展示入口”，真正收费计算必须下钻到子项

排查组套问题时，最容易犯的错是盯着主项金额不放。旧逻辑里，主项往往只是入口或汇总壳，真正决定可收费额度的是子项链路。

普通组套：ConvertGroupToDetail

读取组套定义

先查出主项下面理论上有哪些成员子项，明确拆解边界。

逐子项重建收费对象

不是直接照抄目录价，而是结合年龄、合同单位、组套比例重新算子项单价。

回挂主项附加属性

主项上的减免、特殊自费、公费待遇属性，需要重新分摊到子项上，避免主子项口径不一致。

DR 特殊组套：ConvertDRGroupToDetail

首项 / 非首项分流

根据 isFirst 判断“第一组收费”和“第二组起收费”子项哪部分参与计算。

drCount 汇总基数

先汇总 DR 差异收费的数量基数，再给后续总量取整等老规则使用。

统一取整后回写

不是每个子项各自取整，而是按汇总数量统一取整，再回写到对应收费子项。

CT / PACS 特殊组套：ConvertCTGroupToDetail

先占位，只收一次

hsOnlyOneItem 先记录谁被保留，谁会在后续被淘汰。

三维 / 四维优先级处理

四维出现后，前面暂时保留的三维可能被改判为淘汰项，所以不能只看单条当场结果。

正式生成子项对象

按 CT 价格算法重建收费对象，再把主项附加属性挂回新对象。

反向动作：ConvertDetailToGroup
这个方法跟“主项拆明细”正好相反。它会把已经拆开的子项按 UndrugComb.ID 再聚回主项视角，通常用于某些需要主项展示或回看主项结果的场景。
Rule Table

折价规则表：先认出名字，再知道它会把什么结果改掉

下面这张表不是单纯列常量名，而是把“名字”“何时命中”“代码效果”放在一起，方便你看代码时快速对号入座。

规则 / 常量 它在管什么 代码里的实际效果 开发排查时要注意
Restrictingfee 普通项目数量限制 查历史收费次数，算剩余额度；超限则归零，部分超限则截断数量。 它管的是“剩余额度还能不能收”，不是整单拒绝。
RestrictingfeeZT 分组互斥限制，按组号看同组是否还能继续收费 调用 getRestrictingfeeZT；同组前序项目或历史项目会直接顶掉当前项目资格。 不要把它理解成“所有 ZT 项目都互斥”，真正互斥的是同组号范围。
RestrictingfeeCP 床旁项目限制 更接近同类互斥，前面已有床旁类项目时，当前项目不能再收。 这类问题通常不是同编码累计，而是同类项目之间互斥。
RestrictingfeeTX1 胎心监护类限制 按胎心类项目 / 组套互斥处理，不是简单按同一项目编码累计。 遇到胎心类收费异常时，要连组套链路一起看。
Astrictpackagefee 组套内豁免项 这类项目不参与历史次数扣减，相当于“组套里某些子项不受数量限制”。 如果某个组套子项看起来“没被扣额度”，先确认是否属于豁免项。
FIN_DISCOUNT_FEE 比例折价 + 最高限价 第 1 个全价，第 2 个及以后按比例折价，再受 TOPPRICE 封顶。 不要把它和数量限制混成一条逻辑线；它本质是另一套金额计算法。
7021 当前按体验科室解释 界面层命中数量限制时，不执行数量折价。 这是当前页面采用的沟通口径，排查时要确认现场系统的真实科室含义。
Variables

关键变量解释：看懂这些名字，才能看懂“谁被保留、谁被替换、谁在继续占额度”

旧代码里最容易让人迷糊的不是方法名，而是这些临时集合和中间变量。把它们的角色分清，很多逻辑就不再像黑箱。

hsREOnlyOneItem

重算登记表 旧对象将被替换

被规则逻辑接管、已经完成“重算”的项目登记表。它主要告诉后续流程：原对象不要再继续使用，后面要换成新版本对象。

hsREOnlylistItem

新对象列表 用于补回界面

重算后真正要补回列表或界面的项目集合。可以直接把它理解成“已经按旧折价规则修正完成的新版本对象列表”。

hsNOREOnlyOneItem

普通前序项目 继续占额度

本次收费里已经被保留下来的普通项目集合。后续项目继续计算剩余额度时，会把它们也一起计入“本次已占额度”。

hsZTNOREOnlyOneItem

前序组套子项 跨组套累计

本次收费中、前面组套拆出来并已保留的子项集合。它的意义是：后面的组套继续限次时，也要把这些前序子项算进累计。

GroupNumber

互斥组号 不是全局互斥

分组收费的组号。只有同组号项目之间才真正互斥，所以遇到 ZT 类项目不能笼统判断，必须先确认分组范围。

feetype / LimitNumber / Limitsum

历史次数 总上限 最终剩余额度

feetype 表示历史已收费次数，LimitNumber 表示总上限，Limitsum 表示扣完历史次数和本次前序项目后，当前项目真正还能使用的剩余额度。

Source Locator

源码定位：如果你现在就要进代码，这张表告诉你先打开哪一个方法

下面按“方法属于哪个阶段”“你应该重点看什么”来排，不只是文件名索引，而是排查入口建议。

文件 方法 属于哪一阶段 进去以后优先看什么
ucDisplay.cs SetItem 单条录入入口 看当前项目是怎么被识别为普通项或组套，以及何时触发即时限制收费回算。
ucDisplay.cs SetChargeInfo 界面刷新链 看旧对象何时被删掉，重算后的对象何时补回，以及 7021 等界面层口径在哪拦截。

ucDisplay.cs GetFeeItemList 提交前最终整理 看组套拆解、DR/CT 去重、最终限制收费回算是在什么顺序上串起来的。

实际排查顺序建议： 如果问题是“显示金额不对”，先看 SetChargeInfo；如果问题是“提交后金额又变了”，先看 GetFeeItemList；如果问题是“规则为什么这么算”，再进 Restrictingfee.cs 看算法分支。
